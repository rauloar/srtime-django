PARTE 1: ROL DEL ENGINE V1 (PRODUCCIÓN)

1.1 QUÉ PROBLEMA RESUELVE V1
─────────────────────────────

V1 (attendance_engine.py) es el **sistema de cálculo oficial y autoridad**.
Su responsabilidad es transformar logs crudos de dispositivos ZKTeco 
en métricas diarias de asistencia con estado (Normal, Late, Absent, etc.).

Input:
  • employee_id: int
  • target_date: date (ej: 2026-02-10)

Output:
  • models.DailyAttendance (persistida en BD)
    ├─ status: str (Normal, Late, Early, Absent, Incomplete, etc.)
    ├─ worked_minutes: int (minutos reales trabajados)
    ├─ late_minutes: int (minutos llegó tarde)
    ├─ early_minutes: int (minutos salió temprano)
    ├─ overtime_minutes: int (minutos extra)
    ├─ check_in: datetime
    ├─ check_out: datetime
    └─ [10 campos más para auditoría y contexto]

Problema que resuelve:
  Raw logs (timestamp, punch_type) → Métricas interpretadas (status, minutos)
  
  Ejemplo:
    Input log: [09:20 (check-in), 17:00 (check-out)]
    Horario: 09:00-17:00
    Output: status=Late, late_minutes=15 (después de tolerancia)


1.2 INPUTS ESPERADOS POR V1
──────────────────────────

Precondiciones:
  • Employee debe existir en BD
  • Employee.user_id debe estar poblado
  • Timetable debe existir (resuelto vía schedule_resolver)
  • AttendanceLog puede estar vacío (resultado: Absent)

Flujo de resolución de precondiciones en V1:

  calculate_day(employee_id=123, target_date=2026-02-10)
      ↓
    resolve_schedule(employee_id, target_date)  [delegada a schedule_resolver]
      ├─ Check ScheduleOverride (tabla override)
      ├─ Check EmployeeShift (scope=EMPLOYEE)
      ├─ Check EmployeeShift (scope=DEPARTMENT)
      └─ Default: Implicit rest day (Absent)
      ↓
    return DayContext(is_valid=bool, timetable=Timetable)


1.3 FLUJO INTERNO DE V1 (PASO A PASO)
─────────────────────────────────────

Paso 0: Preparar resultado
  daily, created = DailyAttendance.objects.get_or_create(
    employee_id=employee_id,
    date=target_date
  )
  Resultado: Obtiene registro existente o crea uno nuevo (limpio)

Paso 1: Resolver Schedule
  ctx = resolve_schedule(employee_id, target_date)
  
  ¿Qué hace?
    • Determina qué horario tiene el empleado hoy
    • Retorna DayContext con:
      - timetable object (con on_duty, off_duty, break_minutes, etc.)
      - source: "OVERRIDE" | "EMPLOYEE_SHIFT" | "DEPARTMENT_SHIFT" | "IMPLICIT_REST"
      - is_valid: bool (falso si no hay horario asignado)
  
  Si es_invalido:
    daily.status = "Absent"
    daily.exception_reason = "No schedule configured for this date"
    EARLY RETURN → DailyAttendance(Absent)

Paso 2: Validar Timetable
  if not ctx.is_valid or not ctx.timetable:
    return empty DailyAttendance (Absent)

Paso 3: Obtener Employee
  emp = Employee.objects.filter(id=employee_id).first()
  if not emp or not emp.user_id:
    return empty DailyAttendance (Absent)

Paso 4: Buscar Logs del Día
  logs = get_logs(emp.user_id, ctx.search_start, ctx.search_end)
  
  Search window:
    - Para horarios fijos: on_duty_time ± tolerancia
    - Para horarios flexibles: check_in_start → check_out_end
  
  Si no hay logs:
    daily.status = "Absent" (para fijos) | "Incomplete" (para flexibles)
    return early

Paso 5: Detectar tipo de horario (Fixed vs Flexible)

  V1 soporta AMBOS tipos:

  A) HORARIO FIJO (is_flexible=False)
     ├─ on_duty_time: "09:00:00" (obligatorio)
     ├─ off_duty_time: "17:00:00" (obligatorio)
     ├─ break_minutes: 60 (descantos a restar)
     ├─ rounding_rule: "none" | "5min" | "10min" (redondeo)
     ├─ late_allow_minutes: 10 (tolerancia entrada)
     └─ early_leave_allow_minutes: 10 (tolerancia salida)

  B) HORARIO FLEXIBLE (is_flexible=True)
     ├─ check_in_start: "07:00:00" (ventana apertura)
     ├─ check_out_end: "20:00:00" (ventana cierre)
     ├─ required_minutes: 480 (horas que debe pasar dentro de ventana)
     └─ [rounding y breaks aún aplicables]

Paso 6A: CÁLCULO HORARIO FIJO
─────────────────────────────

  6A.1 Buscar primer check-in (punch=0, 4, 8)
       daily.check_in = primer log con state in [0, 4, 8]
  
  6A.2 Buscar último check-out (punch=1, 5, 9)
       daily.check_out = último log con state in [1, 5, 9]
  
  6A.3 Aplicar rounding (si configurado)
       if timetable.rounding_rule == "5min":
         redondear check_in y check_out a múltiplos de 5
  
  6A.4 Calcular Late
       if check_in > on_duty_time:
         late_raw = (check_in - on_duty_time).total_seconds() / 60
         late = max(0, late_raw - late_allow_minutes)
         if late > 0: status = "Late"
  
  6A.5 Calcular Early Leave
       if check_out < off_duty_time:
         early_raw = (off_duty_time - check_out).total_seconds() / 60
         early = max(0, early_raw - early_leave_allow_minutes)
         if early > 0: status = "Early Leave" (o combinado con Late)
  
  6A.6 Calcular Worked Minutes
       if check_in and check_out:
         duration = (check_out - check_in).total_seconds() / 60
         worked_minutes = duration - break_minutes
  
  6A.7 Calcular Overtime
       if check_out > off_duty_time:
         overtime_raw = (check_out - off_duty_time).total_seconds() / 60
         overtime = max(0, overtime_raw)
         if overtime >= overtime_threshold:
           add to status "Normal, Overtime"

Paso 6B: CÁLCULO HORARIO FLEXIBLE
──────────────────────────────────

  6B.1 Iterar logs en pares (entrada/salida)
       current_in = None
       total_worked = 0
       
       for log in logs:
         if log.punch in [0, 4, 8]:  # Check-in
           if current_in is None:
             current_in = log.timestamp
         elif log.punch in [1, 5, 9]:  # Check-out
           if current_in:
             duration = (log.timestamp - current_in).total_seconds() / 60
             total_worked += duration
             current_in = None
  
  6B.2 Resultado flexible
       worked_minutes = total_worked
       status = "Worked" si trabajó algo, "Incomplete" si no
       [NO se calcula late/early/overtime en flexibles]

Paso 7: Guardar DailyAttendance
  daily.save()

Paso 8: OPCIONAL - Ejecutar Shadow Mode
  try:
    from .shadow_mode_service import ShadowModeService
    shadow = ShadowModeService()
    shadow.validate_daily_calculation(employee_id, target_date, daily)
  except:
    # Errores de shadow nunca afectan V1
    pass

Resultado: DailyAttendance persistida en BD (autoridad oficial)


1.4 CÁLCULO EN BATCH (calculate_period)
───────────────────────────────────────

Función: calculate_period(start_date, end_date, department_id=None)

Responsabilidad: Iterar sobre rango de fechas y empleados

Algoritmo:
  1. Filtrar empleados activos
     if department_id: employees = employees.filter(department=dept)
  
  2. Refinar: solo empleados CON EmployeeShift asignado
     valid_employees = [e for e in all_employees if e has EmployeeShift]
     skipped = [e for e in all_employees if NOT has EmployeeShift]
  
  3. Para cada empleado + fecha:
     for emp in valid_employees:
       for date in date_range(start, end):
         try:
           daily = calculate_day(emp.id, date)
           results.append(daily)
         except error:
           skipped.append({'employee': emp, 'date': date, 'reason': error})
  
  4. Retorna:
     (results: List[DailyAttendance], skipped_employees: List[dict])

Ejemplo output:
  {
    "message": "✅ Calculated 45 records...",
    "summary": {
      "processed_records": 45,
      "skipped_employees": 2,
      "absence_reasons": {
        "NO_SHIFT_ASSIGNED": [emp_id_5, emp_id_12]
      }
    }
  }

2.1 QUÉ PROBLEMA RESUELVE V2
───────────────────────────

V2 (attendance_engine_v2.py) es el **motor de validación experimental**
que corre en PARALELO a V1, con ARQUITECTURA DIFERENTE pero MISMAS PRECONDICIONES.

Propósito: Validar nuevo enfoque de cálculo sin comprometer producción

Input: IDÉNTICO a V1
  • employee_id: int
  • target_date: date

Output: IDÉNTICO a V1
  • models.DailyAttendance (NO persistida por V2 en shadow mode, solo comparada)
    [mismos campos que V1]

Diferencia conceptual: V2 NO es invocado directamente por usuarios.
V2 es invocado por ShadowModeService DESPUÉS de que V1 ya calculó y guardó.


2.2 EN QUÉ DIFIERE V2 DEL V1 (CONCEPTUALMENTE)
──────────────────────────────────────────────

ARQUITECTURA DIFERENTE:

  V1: Monolítico
    ├─ schedule resolution inline
    ├─ lógica fixed/flexible mezclada en función
    ├─ cálculo directo sobre logs
    └─ impuro (accede BD directamente)
  
  V2: Modular (Strategy Pattern)
    ├─ schedule resolution → delegada
    ├─ procesadores separados (StructuredProcessor, FlexibleProcessor)
    ├─ DayContext construido separadamente
    └─ más puro (ProcessorContext como parámetro)

Ejemplo: cálculo de late_minutes en V1 vs V2

  V1 (inline):
    if daily.check_in > ctx.on_duty_dt:
      late_delta = (daily.check_in - ctx.on_duty_dt).total_seconds() / 60
      daily.late_minutes = int(late_delta)
      if tt.late_allow_minutes:
        daily.late_minutes = max(0, daily.late_minutes - tt.late_allow_minutes)
  
  V2 (delegado a processor):
    # StructuredProcessor.process():
    # Recibe ProcessorContext, ejecuta lógica PURA (sin ORM)
    # Retorna DailyCalculationResult
    def process(ctx: ProcessorContext) -> DailyCalculationResult:
      # regla: late_minutes = max(0, check_in_offset - tolerance)
      late = max(0, check_in_offset - ctx.late_allow_minutes)

2.4 PROCESADORES EN V2 (STRATEGY PATTERN)
─────────────────────────────────────────

Arquitectura de V2: Usa Strategy Pattern para delegar cálculo

  V2 Engine:
    1. Construye ProcessorContext
    2. Selecciona processor (Fixed o Flexible)
    3. Llama processor.process()
    4. Mapea resultado a modelo

Existencia de procesadores:

  A) StructuredProcessor (para horarios FIJOS)
     - Ubicación: core/services/processors/structured_processor.py
     - Responsabilidad: Cálculos de horarios fijos
     - Lógica similar a V1 pero separada y pura
  
  B) FlexibleProcessor (para horarios FLEXIBLES)
     - Ubicación: core/services/processors/flexible_processor.py
     - Responsabilidad: Cálculos de horarios flexibles
     - Lógica pura (sin estado)

Flujo de procesamiento:

  ProcessorContext
        ↓
  get_processor(is_flexible=True/False)
        ↓
  FlexibleProcessor / StructuredProcessor
        ↓
  processor.process(context)
        ↓
  DailyCalculationResult (objeto puro)
        ↓
  map to DailyAttendance model

3.3 EDGE CASES MANEJADOS
────────────────────────

Edge Case 1: Empleado sin EmployeeShift
  V1: Salta (NO_SHIFT_ASSIGNED en calculate_period)
  V2: Idem (verificar si calculate_period_v2 tiene lógica similar)

Edge Case 2: Turno sin ShiftTimetable para ese día
  V1: status = "Absent" (SHIFT_TIMETABLE_MISSING_DAY)
  V2: Idem (delegado a resolve_schedule_unified)

Edge Case 3: Logs cruzados a medianoche (overnight shift)
  V1: Soporta via is_cross_day en DayContext
       on_duty: 22:00 (hoy)
       off_duty: 06:00 (mañana)
  V2: Idem

Edge Case 4: ScheduleOverride sobre horario actual
  V1: Override tiene MÁXIMA prioridad (resolve_schedule chequea primero)
  V2: Idem (mismo resolve_schedule_unified)

Edge Case 5: Rounding cuando se redondea a hora siguiente
  V1: round_time() maneja redondeos hacia arriba/abajo
      rule="5min" → redondea al múltiplo de 5 más cercano
  V2: Delegado a procesador (verificar ProcessorContext.rounding_rule)

Edge Case 6: Múltiples check-in/out en mismo día (entrada/salida múltiples)
  V1 Fixed: Toma PRIMER check-in y ÚLTIMO check-out
            (ignora entradas/salidas intermedias)
  
  V1 Flexible: ACUMULA duración de todos los pares in/out
               (por eso total_worked es más preciso)
  
  V2: Verificar si los procesadores hacen lo mismo


3.4 CASOS DONDE V1 Y V2 PODRÍAN DIVERGIR
──────────────────────────────────────────

Potenciales puntos de divergencia:

1. ROUNDING RULES
   Si V1 redondea diferente que StructuredProcessor
   → late_minutes, early_minutes podrían diferir
   
   Ejemplo:
     V1 redondea: 08:59 → 09:00 (round up)
     V2 redondea: 08:59 → 08:55 (floor to 5min)
     
   Efecto: late_minutes divergen

2. ESTADO DE HORARIOS FLEXIBLES
   V1: status = "Incomplete" si worked=0, "Worked" si worked>0
   V2: status depende de blocks_count (puede diferir si lógica parse distinta)

3. ORDER OF OPERATIONS
   V1: Check Late → Check Early → Calculate Overtime
   V2: [Verificar orden en StructuredProcessor]
   
   Si el orden es diferente, status podría ser diferente
   cuando hay múltiples condiciones (ej: "Late" vs "Late, Early Leave")

4. TOLERANCIA Y THRESHOLD
   V1 calcula:
     late_minutes = max(0, late_raw - tolerance)
   
   V2 (en procesador):
     late_minutes = max(0, check_in_offset - ctx.late_allow_minutes)
   
   Podrían diferir si el offset se calcula distinto

5. FLEXIBLES: BÚSQUEDA DE CHECK-IN/OUT
   V1 flexible: acumula duraciones de pares in/out consecutivos
   V2 flexible: [Verificar en FlexibleProcessor]
   
   Si la lógica de emparejamiento (in→out) es distinta:
     V1 resultado: 480 min
     V2 resultado: 470 min
   
   Diferencia: 10 minutos

PARTE 4: SHADOW MODE (CÓMO TRABAJA)
================================================================================

4.1 QUÉ ES SHADOW MODE EN ESTE SISTEMA
──────────────────────────────────────

Shadow mode es un **PATRÓN DE VALIDACIÓN** donde:
  • V1 ejecuta → Resultado guardado en BD (OFICIAL)
  • V2 ejecuta en PARALELO → Resultado comparado CON V1 (NO GUARDADO)
  • Diferencias registradas para auditoría

Propósito:
  • Validar V2 nuevo engine
  • Detectar regresiones antes de migrar
  • Recopilar evidencia de que V2 es seguro
  • Sin riesgo (V2 fallas NO afectan producción)

Garantías de Shadow Mode:
  ✓ V2 falla → error logged, V1 sigue OK
  ✓ V2 diferencia → registrada, V1 guardado oficial
  ✓ Zero side effects en datos de producción
  ✓ Opcionalmente completamente deshabilitado (settings)


4.2 CUÁNDO Y CÓMO SE EJECUTA V2
───────────────────────────────

Flujo exacto (en código):

  A) Usuario ejecuta cálculo:
     POST /api/v1/attendance/calculate/
     
  B) Backend invoca calculate_period()
     que itera sobre empleados × fechas
  
  C) Para cada fecha:
     daily_v1 = calculate_day(employee_id, target_date)
     └─ Dentro de calculate_day():
        try:
          shadow = ShadowModeService()
          shadow.validate_daily_calculation(
            employee_id=employee_id,
            target_date=target_date,
            v1_daily_attendance=daily_v1  # ya guardado
          )
        except Exception:
          pass  # shadow errors NUNCA se propagan

Precondiciones para que V2 ejecute:
  1. ATTENDANCE_SHADOW_ENABLED = True en settings
     (por defecto False en DEV, pero puede habilitarse)
  
  2. V1 debe haber completado sin excepciones
  
  3. ShadowModeService debe poder instanciar

Si V2 no se ejecuta (shadow deshabilitado):
  • Cálculo sigue igual
  • Algunos logs dicen "Shadow mode disabled"
  • Zero overhead


4.3 COMPARACIÓN DE RESULTADOS
─────────────────────────────

Cómo se comparan V1 vs V2:

Paso 1: Extraer datos V1
  v1_results = {
    'status': v1_daily.status,
    'worked_minutes': v1_daily.worked_minutes,
    'late_minutes': v1_daily.late_minutes,
    'early_minutes': v1_daily.early_minutes,
    'error': None,
  }

Paso 2: Extraer datos V2
  v2_daily = calculate_day_v2(emp_id, date, persist=False)
  v2_results = {
    'status': v2_daily.status,
    'worked_minutes': v2_daily.worked_minutes,
    'late_minutes': v2_daily.late_minutes,
    'early_minutes': v2_daily.early_minutes,
    'error': None,
  }

Paso 3: Comparar campo por campo
  tolerance = 1 minute
  
  COMPARACIÓN:
    if v1_status != v2_status:
      differences.append(f"Status mismatch: {v1_status} vs {v2_status}")
    
    if abs(v1_worked - v2_worked) > tolerance:
      differences.append(f"Worked minutes differ: {diff}")
    
    if abs(v1_late - v2_late) > tolerance:
      differences.append(f"Late minutes differ: {diff}")
    
    if abs(v1_early - v2_early) > tolerance:
      differences.append(f"Early minutes differ: {diff}")

Paso 4: Construir ShadowComparison
  return ShadowComparison(
    employee_id, target_date,
    v1_status, v1_worked, ...,
    v2_status, v2_worked, ...,
    has_differences=bool,
    differences=[list],
    comparison_timestamp=now()
  )

────────────────────────────

QUÉ SE PERSISTE:
  ✓ DailyAttendance de V1 (SIEMPRE, en BD)
    └─ Esto es lo oficial

QUÉ NO SE PERSISTE ACTUALMENTE:
  ✗ ShadowComparison (NO se guarda en BD)
  ✗ DailyAttendance de V2 (NO se guarda)

      Si hubiera tenido table ShadowCalculation en models_shadow.py,
      se habría guardado; pero en la práctica, eso se comentó/deshabilitó.

  // Si hay diferencias
  logger.warning(f"Shadow: {emp_id} @ {date} → diff={minutes}min ({type})")
  
  // Si hay error
  logger.error(f"Shadow mode validation failed: {error}")


4.5 IMPACTO REAL EN CÁLCULO PRINCIPAL
─────────────────────────────────────

V2 NO impacta V1 de ninguna forma intencional:

  • V1 no espera a V2 (ejecución en secuencia, no paralela)
  • V1 no usa resultados de V2
  • V1 no modifica su lógica basado en V2
  • Si V2 falla, V1 continúa OK

Peor caso posible:
  • V2 exception → logging error → shadow service continúa
  • V1 resultado se guarda COMPLETO
  • Usuario VE exactamente lo mismo

Mejor caso (el común):
  • V2 ejecuta sin problemas
  • Compara con V1: resultados idénticos
  • Shadow logger dice "OK, no differences"

5.3 QUÉ PASA SI V1 Y V2 DIFIEREN
─────────────────────────────────

Paso 1: Diferencia detectada por ShadowModeService
  difference_minutes = 410 - 420 = -10
  has_differences = True

Paso 2: Diferencia registrada en log
  logger.warning(
    f"Shadow: emp_123 @ 2026-02-01 → diff=-10min (MINOR)"
  )

Paso 3: Usuario sigue viendo dato de V1
  DailyAttendance.worked_minutes = 420 ← V1 OFICIAL

Paso 4: Desarrollador re-investiga
  "¿Por qué V2 calcula -10 minutos menos?"
  
  Posibles causas:
  a) V2 está considerando algo que V1 no (ej: nuevo campo oculto)
  b) V2 tiene bug en rounding (ej: redondea diferente)
  c) V1 tiene bug que V2 encontró
  d) Datos de época diferentes (logs modificados)

Paso 5: Decisión
  • Si V2 tiene razón: Arreglar V2 lógica
  • Si V1 tiene razón: Arreglar V2 lógica
  • Si ambos son válidos de formas diferentes: Decidir cuál prevalece

Paso 6: Verificación
  Volver a ejecutar, esperar a que ShadowComparison sea idéntico

PARTE 7: CONCLUSIÓN TÉCNICA
================================================================================

7.1 QUÉ APORTA ESTA ARQUITECTURA DUAL
───────────────────────────────────────

Beneficios de tener V1 + V2:

1. SEGURIDAD EN MIGRACIÓN (Migration Safety)
   Problema: Cambiar lógica crítica arriesga datos
   Solución: V2 corre en paralelo sin riesgo
   
   Beneficio: Detectar bugs en V2 ANTES de reemplazar V1
             Zero downtime para cambios de lógica

2. VALIDACIÓN SIN RIESGO (Zero-Risk Validation)
   V1: Autoridad establecida
   V2: Experimento seguro
   
   Si V2 falla → solo logger vuelca, V1 sigue OK
   Si V2 acierta → datos acumular confianza

3. TESTING EN PRODUCCIÓN (Production Testing)
   Teoría VS Realidad:
     • Tests en CI/CD cubren casos conocidos
     • Shadow mode ejecuta en datos REALES
     • Detecta edge cases del mundo real
   
   Ejemplo: Test dice "Normal day works", shadow executa
            con 5 años de data real → encuentra rounding edge case

4. CONTINUIDAD OPERACIONAL (Operational Continuity)
   Si V1 tiene bug descubierto:
     • No afecta pasado (datos ya guardados)
     • Shadow puede aún comparar futuro
     • Permite decisión sobre qué hacer
   
   Si V2 promete mejor algoritmo:
     • Shadow mode acumula evidencia
     • Una vez confiable, swappear V1←→V2

5. AUDITABILIDAD Y CONFORMIDAD
   ShadowComparison proporciona:
     • Quién calculó qué
     • Qué versión de engine
     • Si hubo divergencias
     • Rastro de cambios

   Para cumplimiento normativo (Chile, España, etc.)
   que exige auditoría de cálculos críticos.

6. REFACTORING CONTROLADO (Controlled Refactoring)
   Problema original: V1 monolítico, difícil de cambiar
   Solución: V2 con Strategy Pattern, modular
   
   Beneficio: V2 demuestra mejora estructural
             Cuando demostrado, reemplaza V1
             Sin riesgo de regresión


7.2 RIESGOS QUE EVITA ESTA ARQUITECTURA
────────────────────────────────────────

Riesgos mitigados:

1. REGRESIÓN EN CÁLCULOS CRÍTICOS
   Riesgo: Cambiar lógica, "olvidar" un edge case
   Mitigación: V2 en shadow, compare automático
   Resultado: Edge cases encontrados PRERELEASE

2. DATOS CORRUPTOS POR CAMBIOS
   Riesgo: V2 bug → datos guardan incorrectos
   Mitigación: V2 no persiste en shadow mode
   Resultado: V1 intacto, tan malo no es

3. PÉRDIDA DE AUDITORÍA
   Riesgo: Cambios sin registro de quién, cuándo
   Mitigación: ShadowComparison loguea cada cálculo
   Resultado: Trazabilidad completa

4. MIGRACIÓN FALLIDA (Fallback Imposible)
   Riesgo: Cambiar a V2, descubrir problema, no poder volver
   Mitigación: V1 y V2 coexisten, puede volverse fácil
   Resultado: A/B testing productivo


7.3 ESCENARIOS DONDE ES ESPECIALMENTE ÚTIL
───────────────────────────────────────────

Este patrón (dual engine + shadow mode) es especialmente
útil cuando:

1. Sistema crítico (payroll, compliance)
   Razón: Un cálculo equivocado afecta salarios
   Utilidad: Shadow mode detecta antes de pesar
   
   Nuestro caso: Asistencia es input a nómina
   → Shadow mode ALTAMENTE útil

2. Lógica matemática compleja
   Razón: Edge cases difíciles de prever
   Utilidad: Producción = testing ground
   
   Nuestro caso: Overlapping shifts, rounding, tolerancias
   → V2 con procesadores modulariza complejidad

3. Cambios de algoritmo legales/normativos
   Razón: Nueva ley requiere cambiar cálculo
   Utilidad: Demostrar conformidad via shadow
   
   Nuestro caso: Chile cambió reglas, shadow valida

4. Auditoría de datos históricos
   Razón: Verificar si cálculos antiguos eran correctos
   Utilidad: Ejecutar V2 sobre data vieja, comparar V1
   
   Nuestro caso: "¿Los cálculos de 2023 fueron correctos?"
   → Ejecutar V2 sobre archivo backup, comparar

5. Machine Learning (futura extensión)
   Razón: Próximo V3 podría usar ML
   Utilidad: V3 ejecuta en shadow, valida antes de producción
   
   Nuestro caso: "V3 con ML para predicción de inasistencia"
   → Shadow mode preparado para ello


7.4 LIMITACIONES Y CONSIDERACIONES
──────────────────────────────────

Limitaciones del diseño actual:

1. ShadowComparison NO se persiste
   Problema: Historial de comparaciones perdido
   Solución: Implementar ShadowCalculation table
   Estado: Existe modelo comentado, no activado

2. Shadow mode es SÍNCRONO
   Problema: Cálculo tarda 2x (V1 + V2 secuencial)
   Solución: V2 en background (Celery job)
   Estado: DEV no lo justifica aún

3. Processadores de V2 NO están separados en archivo
   Problema: Difícil testear procesadores aisladamente
   Solución: Crear core/services/processors/base.py
   Estado: Estructura existe pero tests limitados

4. Sin feedback UI para diferencias
   Problema: Usuario no ve "Jey, V2 calculó diferente"
   Solución: Endpoint /api/v1/shadow/comparisons/
   Estado: No implementado, solo logs

5. Rounding rules complejo, no totalmente validado
   Problema: "5min" rounding podría divergir
   Solución: Tests más granulares
   Estado: Tests existen pero podrían ser más exhaustivos


7.5 CONCLUSIÓN FINAL
─────────────────────

RESUMEN:

El sistema SRTime utiliza una arquitectura DUAL ENGINE (V1 + V2)
con SHADOW MODE para validar versiones nuevas del cálculo
sin riesgo de datos corruptos.

  • Motor OFICIAL y AUTORIDAD

  2. Detección de bugs en mundo real
  3. Facilita migración a V2 en futuro
  4. Auditoría y conformidad regulatoria
