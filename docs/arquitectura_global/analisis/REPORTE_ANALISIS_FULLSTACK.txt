1. RELACIÓN CORE ↔ BACKEND

1.1 ARCHITECTURAL BOUNDARIES (CORE vs Services/Controllers)
─────────────────────────────────────────────────────────────

DIRECCIÓN DE DEPENDENCIAS:
  
  Backend Layers:
    Views/Viewsets (controllers)
        ↓ consume
    Services (calculate_day, calculate_period)
        ↓ import/call
    CORE Engines (V1, V2)
        ↓ compute
    Models (DailyAttendance, Employee, etc.)

  Patrón: Unidireccional (Views → Services → Engines)
  No hay retorno (CORE no ve Views)
  Esto es CORRECTO


CONTRATOS EXPLÍCITOS ENTRE CORE Y BACKEND:

  Contract C1: "calculate_day(emp_id, date) → DailyAttendance"
    Input: employee_id (int), target_date (date)
    Output: DailyAttendance model (persisted in DB)
    Garantía: Función retorna siempre (nunca None)
    Usado por: views_attendance.calculate_single_day()
    
  Contract C2: "calculate_period(start, end, dept) → (results, skipped)"
    Input: start_date (date), end_date (date), department_id (optional int)
    Output: Tuple[List[DailyAttendance], List[skip_info]]
    Garantía: Retorna resultados + skipped employees
    Usado por: views_attendance.calculate_attendance()
    
  Contract C3: "resolve_schedule_unified(emp_id, date) → ResolvedSchedule"
    Input: employee_id (int), target_date (date)
    Output: ResolvedSchedule (is_valid, timetable, source)
    Garantía: Determinística (siempre mismo resultado)
    Usado por: INTERNAMENTE en V1 y V2 SOLO
    
  Contract C4: "ShadowModeService.validate_daily_calculation(emp_id, date, v1) → Comparison"
    Input: employee_id, target_date, v1_daily_attendance
    Output: ShadowComparison object
    Garantía: No modifica BD, no afecta V1
    Usado por: viewsets.DailyAttendanceViewSet.shadow_comparison()


SEVERIDAD DE VIOLACIÓN DE CONTRATOS:

  Si View olvida llamar calculate_day():
    → Consecuencia: DailyAttendance no existe
    → Impacto: ALTO (sistema no calcula)
    → Protección: Ninguna (manual)

  Si calculate_day() no persiste:
    → Consecuencia: Datos nunca guardan
    → Impacto: CRÍTICO
    → Protección: Código V1 tiene .save()

  Si resolve_schedule_unified() devuelve diferente resultado para V1 vs V2:
    → Consecuencia: Ambos engines divergen en setup
    → Impacto: ALTO (ShadowComparison no es válida)
    → Protección: Tests, shared function


ANÁLISIS: El CORE es bien aislado.
Riesgos están en "¿quién llamó el CORE?" no en "cómo funciona el CORE".


1.2 INVOCACIÓN DEL CORE DESDE BACKEND
─────────────────────────────────────

Endpoint: POST /api/v1/attendance/calculate/
├─ View: calculate_attendance() en views_attendance.py
├─ Service: calculate_period(start, end, dept)
├─ Engine V1: calculate_day() para cada (emp, date)
├─ Persistencia: DailyAttendance.save()
└─ Retorno: Response con resumen + skipped_employees

Endpoint: GET /api/v1/attendance/reports/daily/?params
├─ View: daily_reports() en views_attendance.py
├─ Lógica: Query DailyAttendance (NO recalcula)
├─ Retorno: Lectura de BD (histórico)
└─ Garantía: Invulnerable a cambios de CORE
   (ya están calculados)

Endpoint: POST /api/v1/daily-attendance/{id}/shadow_comparison/
├─ View: DailyAttendanceViewSet.shadow_comparison()
├─ Service: ShadowModeService.validate_daily_calculation()
├─ Engine V2: calculate_day_v2(persist=False)  [en shadow]
├─ Comparación: V1 vs V2 field-by-field
└─ Retorno: Response con differences (NO persiste)

Endpoint: GET /api/v1/attendance/calculate/<emp_id>/?date=YYYY-MM-DD
├─ View: calculate_single_day(emp_id)
├─ Service: calculate_day(emp_id, date)
├─ Engine V1: Monolítico inline
├─ Persistencia: DailyAttendance.save()
└─ Retorno: Response con resultado + shadow status


PATRÓN DE INVOCACIÓN ACTUAL:
  • V1 se invoca SIEMPRE (autoridad)
  • V2 se invoca VÍA ShadowModeService DESPUÉS
  • V2 failures no afectan V1 (try/except wrapper)
  • Todos los endpoints son síncronos (bloqueantes)


CRÍTICO: INVOCACIÓN ES SÍNCRONA
  Implicación: Si calculate_day() tarda 1s y hay 1000 empleados
             → Respuesta tarda ~1000s (16 min) sin paralelización
  Protección: Ninguna hoy (pero está en límites de lote pequeño)


1.3 DEPENDENCIAS EXTERNAS DEL CORE
───────────────────────────────────

¿Qué necesita CORE para funcionar?

  ✓ Django ORM
    - Filter, ForeignKey relationships
    - .save() en DailyAttendance
    - No hay transacciones explícitas (confía en default)

  ✓ Models (Employee, AttendanceLog, Timetable, EmployeeShift)
    - get_or_create(), filter()
    - Acceso a fields: user_id, timetable.on_duty_time, etc.
    - Si cambia schema de modelo => CORE se rompe

  ✗ NO depende de:
    - Settings del sistema (ATTENDANCE_SHADOW_ENABLED puede ser ignored)
    - Redis/ Cache (offline-first)
    - APIs externas (determinístico)
    - Frontend state (stateless)

IMPLICACIÓN: El CORE es frágil a cambios de:
  • Django ORM syntax (unlikely)
  • Model schema (campos utilizados)
  • Model deletion (ej: eliminar Timetable)

2.1 ENDPOINTS CONSUMIDOS DESDE REACT

Para entender esto, necesito mapear:
"¿Qué endpoint llama la UI?" → "¿Qué servicio?" → "¿Qué CORE?"

ENDPOINT E1: POST /api/v1/attendance/calculate/
├─ UI Consumer: HRDashboard → "Calculate Attendance" page
├─ Frontend Call: axios.post('/api/v1/attendance/calculate/', {start_date, end_date})
├─ Response Format: {
│    message: "✅ Calculated X records",
│    summary: { processed_records, skipped_employees, total_employees_expected },
│    date_range: { start, end, days },
│    skipped_employees: { total, by_reason: {} },
│    processed_analysis: { absence_reasons: {} }
│  }
├─ CORE Involved: V1 (calculate_period → calculate_day loop)
├─ Wait Time: O(n × 1s) = blocking response

ENDPOINT E2: GET /api/v1/attendance/reports/daily/?filters
├─ UI Consumer: HRDashboard → "Daily Reports" page
├─ Frontend Call: axios.get('/api/v1/attendance/reports/daily/', {params})
├─ Response Format: {
│    employee_records: [
│      { employee_id, date, status, worked_minutes, late_minutes, ... }
│    ],
│    filters_applied: {},
│    record_count: N
│  }
├─ CORE Involved: NONE (lectura de DailyAttendance ya calculada)
├─ Wait Time: O(n) = efficient
└─ Risk: Bajo (datos ya en BD)


ENDPOINT E3: GET /api/v1/daily-attendance/{id}/shadow_comparison/
├─ UI Consumer: ? (no se ve claramente en código frontend revisado)
├─ Frontend Call: axios.get('/api/v1/daily-attendance/{id}/shadow_comparison/')
├─ Response Format: {
│    employee_id, date,
│    v1: { status, worked_minutes, late_minutes, early_minutes, error },
│    v2: { idem },
│    comparison: { matches: bool, differences: [], timestamp }
│  }
├─ CORE Involved: V1 (ya en BD) + V2 (shadow on demand)
├─ Wait Time: O(1s) = fast
└─ Risk: Bajo (shadow no persiste)


ENDPOINT E4: POSTy /api/v1/daily-attendance/
├─ UI Consumer: Presumably para crear/actualizar registros
├─ Frontend Call: axios.post('/api/v1/daily-attendance/', {...})
├─ Response Format: Standard DRF response
├─ CORE Involved: NONE (ViewSet CRUD, no cálculo)
├─ Wait Time: ms
└─ Risk: Bajo (simple CRUD)


2.2 CONTRATO IMPLÍCITO: UI ← BACKEND
──────────────────────────────────────

Lo que la UI ESPERA del Backend (sin decirlo):

EXPECTATIVA E1: "DailyAttendance tiene Status enum"
  ✓ V1 asigna: status in ["Normal", "Late", "Early Leave", "Incomplete", "Absent", "Worked"]
  ✗ UI probablemente hardcodea: if (status === 'Late') { show red badge }

  ✓ V1 siempre setea: worked_minutes, late_minutes, check_in, check_out
  ✗ UI probablemente hace: ${record.late_minutes > 0 ? 'Late' : 'Normal'}
  Risk: Si late_minutes es UNDEFINED => UI puede crusharse


EXPECTATIVA E3: "Cálculo es inmediato (síncrono, no queue)"
  ✓ V1 es síncrono, retorna resultado en response
  ✗ UI espera: POST /calculate → response con datos en segundo
  Risk: Si movemos a async/queue => UI esperaría polling (breaking change)


EXPECTATIVA E4: "Skipped employees NO son error, son aviso"
  ✓ Endpoint retorna: skipped_employees: { total, by_reason }
  ✗ UI probablemente los muestra como "warning" o ignorados
  Risk: Si cambiamos semántica de skip => UI muestra distinto

2.3 ACOPLAMIENTOS CRÍTICOS (UI ← BACKEND FIELDS)
─────────────────────────────────────────────────

El frontend ASUME estos campos en DailyAttendance JSON:

  ✓ status: string enum (UI usa para iconos/colores)
    └─ Si status="Unknown" → UI breaks

  ✓ worked_minutes: int (UI suma para reportes)
    └─ Si NULL → agregación rompe

  ✓ late_minutes: int (UI filtra/suma/reporta)
    └─ Si NULL → comparaciones fallan

  ✓ employee_id: int (UI foreign key)
    └─ Si NULL → relación breaks

  ✓ date: string ISO (UI ordena/filtra por fecha)
    └─ Si formato cambia → UI parsing falla

  ✓ check_in, check_out: datetime optional (UI muestra horarios)
    └─ Si NULL cuando debería existir → UI muestra "sin entrada/salida"

  ? early_minutes, overtime_minutes (¿UI los usa?)
    ├─ Probables, pero sin verificación en código frontend leído
    └─ Riesgo: Cliente (HR user) espera verlos y se confunde si desaparecen

  ? exception_reason: string optional (¿UI lo muestra?)
    ├─ V1 popula cuando status=Absent
    └─ Riesgo: Si UI depende de esto, cambio rompe


SEVERIDAD: MEDIO-ALTO
Razón: Si V1 cambia output, múltiples pantallas podrían fallar

3.1 FLUJO COMPLETO: "CALCULAR ASISTENCIA PARA PERÍODO"
────────────────────────────────────────────────────────

Trigger: User clicks "Run Calculation" button in HR Dashboard

PASO 1: Frontend - Formulario
  User selects:
    • Start Date: 2026-02-01
    • End Date: 2026-02-07
    • Department: (optional)
  Clicks: "Calculate"

PASO 2: Frontend - Validación y Request
  JavaScript:
    1. Valida dates (client-side)
    2. Arma JSON payload:
       { start_date: "2026-02-01", end_date: "2026-02-07", department_id: 1 }
    3. POST /api/v1/attendance/calculate/
    4. Spinner: "Calculating..." appears

PASO 3: Backend - Views Layer
  views_attendance.calculate_attendance(request) CALLED
    1. Parse request.data → start_date, end_date, dept_id
    2. Valida dates format (ValueError → return 400)
    3. Llama: calculate_period(start, end, dept)  [SERVICE CALL]
    4. Recibe: (results, skipped_employees)

PASO 4: Backend - Services Layer (CRITICAL)
  calculate_period(start_date, end_date, dept_id):
    1. Filter employees: Employee.objects.filter(...)
    2. Filter shifts: EmployeeShift.objects.filter(...).distinct()
    3. Split: validOs vs skipped_no_shift
    4. FOR each employee IN valid_employees:
         FOR each date IN date_range:
           CALL: calculate_day(emp.id, date)  [CORE V1]
           Append resultado a results list
           IF exception: Agrega a skipped_employees, continúa
    5. Retorna: (results: List[DailyAttendance], skipped: List)

PASO 5: CORE Layer (ENGINES) - MAIN CALCULATION
  calculate_day(emp_id, date) para CADA (emp, date):
    A. Prep:
       1. DailyAttendance.objects.get_or_create(emp_id, date)
       2. Reset all fields (status="Absent" default)
    B. Resolve Schedule:
       1. resolve_schedule_unified(emp_id, date) [DETERMINÍSTICO]
       2. Si not valid → status="Absent", save, return
    C. Fetch Employee & Logs:
       1. Employee.objects.filter(id=emp_id).first()
       2. get_logs(user_id, search_start, search_end)
    D. Calculate (dual path):
       ✓ Si flexible:
         • Suma duraciones punch pairs
         • Status = "Worked" | "Incomplete"
         • late_minutes=0, early_minutes=0, overtime=0
       ✓ Si fixed:
         • Detecta check_in/out
         • Aplica rounding si configurado
         • Calcula late, early, overtime
         • Status = "Normal" | "Late" | "Early Leave" | etc.
    E. Persistencia:
       1. daily.save() → DB
    F. Shadow Mode (optional):
       1. ShadowModeService().validate_daily_calculation(...)
       2. Compara V1 vs V2
       3. Logguea differences
       4. NO persiste (safe)

PASO 6: Backend - Aggregation y Response
  En views_attendance.calculate_attendance():
    1. Procesa results[] y skipped[] para response
    2. Agrupa skipped por reason
    3. Analiza absence_reasons
    4. Return Response(200):
       {
         message: "✅ Calculated X records",
         summary: { processed, skipped, expectations },
         date_range: { start, end, days },
         skipped_employees: { total, by_reason },
         processed_analysis: { absence_reasons }
       }

PASO 7: Frontend - Response Handling
  JavaScript:
    1. Response received
    2. Spinner: hide
    3. Muestra: "Successfully calculated X records"
    4. Render: Results table
    5. Columns: Employee, Days Processed, Days Present, Days Absent, Total Worked
    6. UI actualiza: Local state con datos de response

PASO 8: Frontend - Display & Navigation
  User puede:
    ✓ Ver resultados en tabla
    ✓ Expandir empleado → ver días individuales?
    ✓ Filtrar resultados
    ✓ Export a CSV?
    ✓ Navegar a otro período → back to PASO 1

PASO 9 (OPCIONAL): Frontend - Detalle de un Día
  Si user clickea un employee en resultado:
    1. Navega a: /daily-attendance/{daily_id}
    2. Frontend: GET /api/v1/daily-attendance/{id}/
    3. Muestra: status, worked, late, early, check_in, check_out, exception_reason
    4. Botón opcional: "View Shadow Comparison"
       → GET /api/v1/daily-attendance/{id}/shadow_comparison/
       → Muestra: V1 vs V2 side-by-side (si están enabled)

FINAL: User vuelve a dashboard o navega a otra sección


ANÁLISIS:
  ✓ Flujo es lineal y claro
  ✓ Puntos de falla identificables:
    - DB connection (step 4)

4. ROBUSTEZ DEL SISTEMA INFORMATIVO
================================================================================

4.1 ¿QUÉ PASA CON DATOS INCOMPLETOS?
──────────────────────────────────────

Escenario S1: Empleado sin logs para un día
  V1 behavior:
    • resolve_schedule() → valid
    • get_logs() → empty list
    • Si flexible: status="Incomplete", worked_minutes=0
    • Si fixed: status="Absent" o sin cambio
    • Resultado: Se persiste igual
  UI display: Muestra "Incomplete" o "Absent" (correcto)
  Robustez: MEDIA (depende de intención HR)


Escenario S2: Empleado sin EmployeeShift asignado
  V1 behavior:
    • resolve_schedule() → is_valid=False
    • return con status="Absent", exception_reason="Schedule error"
    • NO se calcula (correcto protección)
  Backend: calculate_period() lo salta (logged en skipped_employees)
  UI display: Muestra en "Skipped: NO_SHIFT_ASSIGNED"
  Robustez: ALTA


Escenario S3: Timetable del shift no tiene on_duty_time
  V1 behavior:
    • resolve_schedule() → el timetable se retorna anyway
    • _build_context() → on_duty_dt = None
    • Fixed schedule path: si on_duty_dt is None, late_minutes puede ser 0 o error
  Risk: MEDIO (depende de null handling en V1 code)
  Robustez: MEDIA


Escenario S4: AttendanceLog tiene timestamp NULL
  V1 behavior:
    • get_logs() lo retorna anyway
    • En cálculo: int(log.punch) podría fallar si log.punch=None
    • Try/except wrap in calculate_period() absorbe error
  Risk: BAJO (error logged, skipped)
  Robustez: MEDIA (error absorption pero no informado al user claramente)


Escenario S5: Fecha inválida en request
  UI behavior:
    • Client-side validation probablemente valida
    • Si pasa: Backend datetime.strptime() valida
    • Si error: Return 400 "Invalid date format"
  Robustez: ALTA


CONCLUSIÓN:
  Sistema es ROBUSTo ante datos incompletos.
  Falla gracefully (status="Absent", exception_reason set).
  Pero: UI no siempre muestra exception_reason claromente.


4.2 ¿QUÉ PASA CON RESULTADOS "RAROS PERO VÁLIDOS"?
─────────────────────────────────────────────────────

Escenario R1: worked_minutes = 1440 (24 horas de trabajo)
  V1: Calcula y persiste sin error
  UI: Muestra 1440 (correcto, aunque extremo)
  Robustez: OK


Escenario R2: late_minutes = 120 (2 horas atraso)
  V1: Calcula y persiste
  UI: Muestra "Late" (correcto)
  BUT: ¿Es tan extremo que debería disparar alerta?
  Robustez: OK pero sin alerting


Escenario R3: status = "Late, Early Leave" (ambos condiciones)
  V1: Status es compound string
  UI: Si hace string matching "if (status === 'Late')" → probablemente MATCH
  Risk: BAJO (substring match probablemente funciona)
  Robustez: OK


Escenario R4: check_in/check_out sin timestamps (NULL para flexible)
  V1: Setea a None para flexible (intencional)
  UI: Si asume siempre tiene check_in → muestra null/undefined
  Risk: BAJO (flexible schedule no necesita estos valores)
  Robustez: OK


CONCLUSIÓN:
  Sistema maneja edge cases válidos.
  Pero: Sin "confidence level" en V1, UI no puede alertar "resultado sospechoso".


4.3 ERROR HANDLING Y RESILIENCE
───────────────────────────────

PROTECCIONES EXISTENTES:

  ✓ Level 1 (Views): Try/except en views_attendance
    └─ Valida date format, devuelve 400 si error
    └─ Captura exceptions de calculate_period()

  ✓ Level 2 (Services): Try/except en calculate_period()
    └─ Continúa si un día/empleado falla
    └─ Loguea error y omite el registro

  ✓ Level 3 (Core/Engines): Try/except en calculate_day()
    └─ Errores ORM capturados
