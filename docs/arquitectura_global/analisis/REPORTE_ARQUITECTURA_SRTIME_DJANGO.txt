1. RESUMEN EJECUTIVO
================================================================================

SRTime Django es un sistema de gestión de asistencia laboral BASADO EN DISPOSITIVOS
ZKTECO (biometría), diseñado como aplicación full-stack monolítica (Django + React).

MADUREZ: ALFA (explícitamente documentado en docs/README.md)
ESTADO PRODUCTIVO: NO APTO PARA PRODUCCIÓN

Características clave:
• Backend: Django 6.0.1 + DRF + JWT, PostgreSQL
• Frontend: React 18.2.0 + TypeScript + Vite (embebido en Django static)
• Motor de cálculo de asistencia dual (V1 + V2 en shadow mode)
• Auditoría de ediciones manuales
• Integración con dispositivos biométricos ZKTeco vía librería pyzk

CRÍTICOS OBSERVADOS:
- Credenciales hardcodeadas en plaintext (login.json, .env)
- CORS y CSRF inseguros para desarrollo (aplicados en settings)
- DEBUG=True, ALLOWED_HOSTS=['*'] en settings.py
- Archivos de backup con datos sensibles en repositorio
- No hay containerización (sin Dockerfile/docker-compose)
- Tests incompletos y sin CI/CD

PUNTUACIÓN MADUREZ: 3/10 (reflejador de estado alfa, arquitectura compleja pero inmadura)

================================================================================
2. DESCRIPCIÓN FUNCIONAL DEL SISTEMA
================================================================================

PROPÓSITO PRINCIPAL:
Calcular asistencia laboral a partir de marcaciones biométricas de empleados en
dispositivos ZKTeco, con soporte para múltiples turnos, horarios flexibles, 
excepciones y auditoría de ediciones.

FLUJO DE DATOS CRÍTICO:
  Dispositivo ZKTeco
      ↓ (pyzk polling)
  AttendanceLog (tabla raw: device, user_id, timestamp, status)
      ↓ (AcceptJob: importación batch)
  DailyAttendance (tabla calculada con estado de asistencia)
      ↓ (APi JSON para React)
  Frontend (Dashboard + Reports)

ENTIDADES FUNCIONALES:
1. Organización: Company, Department, Position, Zone, Employee
2. Dispositivos: Device (ZKTeco), User (en dispositivo), BiometricTemplate
3. Horarios: Timetable (horario diario), Shift (grupo de timetables), 
               ShiftTimetable (Shift asignado a día de semana)
4. Asignaciones: EmployeeShift (scope: EMPLOYEE | DEPARTMENT), ScheduleOverride
5. Ausencias: Leave (licencia), Holiday (feriado nacional)
6. Asistencia: AttendanceLog (raw), DailyAttendance (calculada)
7. Sistemas: Job (trabajos async), JobLog (logs de jobs)

CÁLCULO DE ASISTENCIA:
Entrada: marcaciones del día (check_in/check_out de AttendanceLog)
Proceso:
  1. Resolver horario del empleado (búsqueda: override > shift > default)
  2. Aplicar reglas de jornada: flexible vs fija
  3. Calcular minutos: worked, late, early, overtime
  4. Determinar status: Normal, Late, Early, Absent, Leave, Incomplete
Salida: DailyAttendance con métricas y estado

ENGINES DUALES:
- V1 (attendance_engine.py): Engine principal (producción)
- V2 (attendance_engine_v2.py): Engine validación en shadow mode
Ambos deben usar resolve_schedule_unified() para consistencia

4.2 MODELOS (Django ORM)
────────────────────────

MODELOS CORE (Autoridad única):
• Company, Position, Zone, Department (organizacionales)
• Employee (id=user_id, strings internos vs Django User)
• Device (ZKTeco devices, IP/Puerto)
• User (usuarios EN el device, no confundir con Django User)
• BiometricTemplate (huellas/rostros)

MODELOS DE ASISTENCIA (Cálculo):
• AttendanceLog (raw logs de marcaciones, editables con auditoría)
  - Campos de auditoría: edited_by, edited_at, edited_reason, is_manual
  - Constraints: uix_att_log (device, user_id, timestamp)
  - SIN usar Django User (fields vacíos)

• DailyAttendance (resultados del cálculo)
  - Status: Normal, Late, Early, Absent, Leave, Worked, Incomplete, 
    Excessive, HolidayWorked, RestDay
  - Métricas: worked_minutes, late_minutes, overtime_minutes
  - Forensic fields (engine_version, policy_snapshot, etc.)
  - PROBLEMA: `status` field DUPLICADO en código (líneas 399-401 en models.py)

MODELOS DE HORARIOS (Configuración):
• Timetable (horario diario: hora entrada, hora salida, breaks, etc.)
  - Soporte: flexible vs fixed, rounding rules, overtime thresholds
  - Ventanas: check_in_start/end, check_out_start/end (para flexibles)

• Shift (grupo de horarios: semanal o ciclo largo)
  - cycle_days=0 (semanal) o >0 (ciclo largo)

• ShiftTimetable (relación N:N Shift → Timetable → day_index)

• EmployeeShift (asignación: scope EMPLOYEE | DEPARTMENT)
  - Priority: EMPLOYEE > DEPARTMENT (vía schedule_resolver)

• ScheduleOverride (sobrescritura diaria por empleado)

MODELOS DE AUSENCIAS:
• Leave (licencia/permiso con status: Pending, Approved, Rejected)
• Holiday (feriados)

MODELOS DE SISTEMA:
• Setting (clave-valor)
• Job, JobLog (trabajos async)
• ImportBatch (lotes de importación)

PROBLEMAS OBSERVADOS EN MODELOS:
1. DailyAttendance.status DUPLICADO (líneas 399-401)
2. Sin indexes en DailyAttendance para búsquedas rápidas (solo 3 índices)
3. Employee.user_id es CharField(50), no relación a Django User
4. Falta de cascada en algunos ForeignKey (SET_NULL cuando debería ser CASCADE)
5. Models importadas de otros módulos al final (models_shadow) sin abstracción clara


4.3 SERIALIZERS (DRF)
─────────────────────

Patrón utilizado: Flat ModelSerializer con calculated fields

Ejemplo (EmployeeSerializer):
  - Fields: id, user_id, name, email, phone, SSN (personal)
  - ForeignKey helpers: department_name, position_name (readonly)
  - Calculated: current_shift, current_timetable, schedule_source (SerializerMethodField)
  - Búsqueda por target_date vía context dict

DEFICIENCIAS:
- No validación de datos
- Sin custom validators (ej: user_id único)
- Sin manejo de partial updates
- Sin control de acceso (read_only, permissions)
- AttendanceLogSerializer acepta ediciones sin validación de roles

  'django-insecure-change-me' → fallback si falta env var

  Abre API a cualquier dominio

CRÍTICA (Bloquea producción):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[1] SECRETOS EN REPOSITORIO
    Archivos: login.json, .env, backups/*.json
    Impacto: Acceso no autorizado a BBDD, servicios
    Effort: 2 horas (git filter-branch, rotate credentials)
    Solución:
      • Borrar login.json y backups del historial Git
      • Rotar credenciales in .env
      • Agregar a .gitignore (sin estar trackeado)
      • Usar GitHub Secrets para CI/CD

[2] AUTENTICACIÓN NO FORZADA
    Problema: AllowAny en REST_FRAMEWORK
    Impacto: Cualquiera lee/escribe datos sin login
    Effort: 4 horas (implementar permissions, serializers validation)
    Solución:
      • Cambiar DEFAULT_PERMISSION_CLASSES a IsAuthenticated
      • Implementar permission mixins por ViewSet
      • Validar roles (admin, hr, employee)
      • Implementar row-level filtering (empleado solo ve sus datos)

[3] SETTINGS INSEGUROS
    DEBUG=True, ALLOWED_HOSTS=['*'], CORS_ALLOW_ALL
    Impacto: Information leak, CORS bypass
    Effort: 1 hora (cambiar settings según env)
    Solución:
      • DEBUG = os.getenv('DEBUG', 'False').lower() == 'true'
      • ALLOWED_HOSTS = ['yourdomain.com', 'api.yourdomain.com']
      • CORS_ALLOWED_ORIGINS = [list de dominios]
      • SECURE_SSL_REDIRECT, HSTS en producción

[4] NO HAY CONTAINERIZACIÓN
    Problema: Sin Dockerfile, docker-compose
    Impacto: Deployment frágil, entorno inconsistente
    Effort: 6 horas (crear Dockerfile, compose, workflows)
    Solución:
      • Dockerfile multi-stage (deps → app)
      • docker-compose: postgres, django, redis
      • GitHub Actions para build/push a registry

[5] FALTA VALIDACIÓN PERMISOS
    Problema: Usuarios pueden editar AttendanceLog sin control
    Impacto: Fraude (editar asistencia propia)
    Effort: 3 horas (implementar permission decorators)
    Solución:
      • Solo HR/Admin puede editar logs
      • Guardar editor_user_id (auditoría mejorada)
      • Implementar approval workflow


ALTO (Afecta producción):
━━━━━━━━━━━━━━━━━━━━━━━━
