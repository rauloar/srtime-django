1.1 FORMALIZACION DE INVARIANTES (SIN CAMBIAR CÓDIGO)
──────────────────────────────────────────────────────

PROBLEMA:
  Hoy los invariantes del cálculo de asistencia son IMPLÍCITOS:
  "late_minutes será >= 0" // pero no está documentado
  "worked_minutes está en rango [0, 1440]" // pero sin límite explícito
  "status está en enum cerrado" // pero sin validación en constructor

PROPUESTA CONCEPTUAL:
  Crear documento "CORE INVARIANTS" que enumere:
  
  INVARIANTE I1: "Valores monetarios no negativos"
    • late_minutes >= 0
    • early_minutes >= 0
    • overtime_minutes >= 0
    • worked_minutes >= 0
    
    Justificación: Imposible tener "-5 minutos de atraso"
    Consecuencia: Si viola, => Calculation Alert "NEGATIVE_VALUE"
    Aplicar a: DailyAttendance y DailyCalculationResult

  INVARIANTE I2: "Límites de rango de minutos"
    • worked_minutes <= 1440 (24 horas)
    • late_minutes <= 1440 (no tiene sentido >24h atraso)
    • early_minutes <= 1440
    • overtime_minutes <= 480 (razonable, max 8h extra)
    
    Justificación: Detección temprana de corrupción
    Consecuencia: Si viola, => Calculation Alert "OUT_OF_RANGE"
    Aplicar a: DailyAttendance y DailyCalculationResult

  INVARIANTE I3: "Consistencia de timestamps"
    • check_in < check_out (si ambos existen)
    • check_in >= search_start (log "window" alignment)
    • check_out <= search_end (log window alignment)
    
    Justificación: Detectar logs fuera de ventana o revertidos
    Consecuencia: Si viola, => Calculation Alert "TIMESTAMP_INVALID"
    Aplicar a: Validación en mapeo resultado a modelo

  INVARIANTE I4: "Coherencia flexible vs fixed"
    • Si is_flexible=True:
      - late_minutes DEBE ser 0
      - early_minutes DEBE ser 0
      - overtime_minutes DEBE ser 0
      - status in ["Worked", "Incomplete", "Absent"]
    • Si is_flexible=False:
      - status in ["Normal", "Late", "Early Leave", "Incomplete", ...]
      - late/early/overtime pueden ser >0
    
    Justificación: Garantizar intención de ZKTime.Net alignment
    Consecuencia: Si viola, => Calculation Alert "SCHEDULE_TYPE_MISMATCH"
    Aplicar a: _map_result_to_model()

  INVARIANTE I5: "Status es valor enum finito"
    • status in DEFINED_STATUSES enum
    • Nunca None
    • Nunca string vacío
    
    Justificación: Evitar garbage status
    Consecuencia: Si viola, => Calculation Alert "INVALID_STATUS"
    Aplicar a: Constructor DailyAttendance

BENEFICIO:
  ✓ Documentación executable (tests pueden validar invariantes)
  ✓ Early detection de bugs (invariante viola => alerta)
  ✓ Confianza en integridad de datos
  ✓ Framework para agregar invariantes futuras


1.2 BOUNDARY CONDITIONS EXPLÍCITAS
──────────────────────────────────

PROBLEMA:
  El código tiene muchas "edge cases" sin documentación:
  • ¿Qué pasa si search_window es 0 segundos?
  • ¿Qué pasa si timetable.break_minutes > trabajado?
  • ¿Qué pasa si logger list has duplicate timestamps?
  • ¿Qué pasa si schedule es overnight (22:00-06:00)?

PROPUESTA CONCEPTUAL:
  Crear documento "BOUNDARY CONDITIONS" que defina:

  BOUNDARY B1: "Ventana de búsqueda vacía (0 segundos)"
    Condición: search_start == search_end
    Comportamiento esperado:
      • logs = [] (vacío)
      • status basado en schedule tipo:
        - Fixed: Absent
        - Flexible: Incomplete
      • late_minutes = 0, early_minutes = 0, worked_minutes = 0
    
    Implementación: assert (search_end - search_start) > timedelta(seconds=1)
    Si falla: log "SEARCH_WINDOW_ZERO"

  BOUNDARY B2: "Break > Worked Time"
    Condición: break_minutes > (check_out - check_in)
    Comportamiento esperado:
      • worked_minutes = max(0, duración - break)
      • No puede ser negativo
      • Log "BREAK_EXCEEDS_DURATION"
    
    Implementación: worked_minutes = max(0, duration - break)
    Si falla: Log "BREAK_BOUNDARY_HIT"

  BOUNDARY B3: "Logs duplicados (mismo timestamp)"
    Condición: logs[i].timestamp == logs[i+1].timestamp
    Comportamiento esperado:
      • Tomar PRIMERA ocurrencia para check_in
      • Tomar ÚLTIMA ocurrencia para check_out
      • Log "DUPLICATE_LOG_TIMESTAMPS"
    
    Implementación: Deduplication or warning en get_logs()
    Si falla: Log "DUPLICATE_LOGS_PRESENT"

  BOUNDARY B4: "Cross-day shift (ej 22:00-06:00)"
    Condición: off_duty_time < on_duty_time && is_cross_day=True
    Comportamiento esperado:
      • search_end se extiende a next_day
      • Cálculos incluyen logs de ambos días
      • Verificar que check_out.date() puede ser != target_date
    
    Implementación: is_cross_day flag en DayContext
    Si falla: Log "CROSS_DAY_BOUNDARY"

  BOUNDARY B5: "Empleado sin user_id en BD"
    Condición: Employee.user_id is NULL
    Comportamiento esperado:
      • No puede hacer matching con AttendanceLog
      • status = Absent
      • exception_reason = "NO_USER_ID_MAPPING"
    
    Implementación: Early guard en calculate_day()
    Si falla: Log "EMPLOYEE_NO_USER_ID"

  BOUNDARY B6: "Timetable nulo pero is_valid=True"
    Condición: ctx.is_valid=True pero ctx.timetable=None
    Comportamiento esperado:
      • NUNCA debe ocurrir (es invariante del resolver)
      • Si ocurre: exception_reason = "TIMETABLE_LOST"
      • Status = Absent (safe fallback)
    
    Implementación: assert ctx.timetable is not None if ctx.is_valid
    Si falla: Log "INTERNAL_ERROR_TIMETABLE_LOST"

BENEFICIO:
  ✓ Prepara sistema para edge cases extremos
  ✓ Facilita debugging (sabes qué boundaries revisar)
  ✓ Evita "surprise" comportamientos
  ✓ Base para test de cobertura exhaustiva


1.3 LÍMITES DE DOMINIO NO DECLARADOS
──────────────────────────────────────

PROBLEMA:
  El código asume lo siguiente SIN documentación:
  • Tolerancias en minutos (¿qué es razonable?)
  • Rounding rules (¿por qué 5/10/15/30 min?)
  • Overtime threshold (¿qué es "minimal" overtime?)
  • Break duration (¿máximo realista?)

PROPUESTA CONCEPTUAL:
  Crear documento "DOMAIN LIMITS" que especifique:

  LÍMITE D1: "Tolerancia de atraso"
    • late_allow_minutes: típicamente [0, 15] minutos
    • Rango aceptable: [0, 60] minutos (> 60 = error en configuración)
    • Validar en Timetable.late_allow_minutes de BD
    
    Si viola: Log "TOLERANCE_OUT_OF_BOUNDS"

  LÍMITE D2: "Tolerancia de salida temprana"
    • early_leave_allow_minutes: típicamente [0, 15] minutos
    • Rango aceptable: [0, 60] minutos
    • Validar en Timetable.early_leave_allow_minutes
    
    Si viola: Log "EARLY_LEAVE_TOLERANCE_OUT_OF_BOUNDS"

  LÍMITE D3: "Duración de break"
    • break_minutes: típicamente [0, 120] minutos
    • Rango aceptable: [0, 240] minutos (> 240 = 4h, es irreal)
    • Validar en Timetable.break_minutes
    
    Si viola: Log "BREAK_DURATION_OUT_OF_BOUNDS"

  LÍMITE D4: "Minutos requeridos (flexible)"
    • required_minutes: típicamente 480 (8h)
    • Rango aceptable: [0, 600] minutos (10h max)
    • Validar en Timetable.required_minutes
    
    Si viola: Log "REQUIRED_MINUTES_OUT_OF_BOUNDS"

  LÍMITE D5: "Threshold de overtime"
    • overtime_threshold_minutes: típicamente 480 (8h)
    • Rango aceptable: [0, 600] minutos
    • Validar en Timetable.overtime_threshold_minutes
    
    Si viola: Log "OVERTIME_THRESHOLD_OUT_OF_BOUNDS"

  LÍMITE D6: "Logs por día"
    • Máximo realista: 100 logs/día (50 check-ins/outs)
    • Alerta si > 100: Log "EXCESSIVE_PUNCHES"
    • Alerta si duplicados: Log "DUPLICATE_TIMESTAMPS"
    
    Protección: Evita DoS de memoria en processors

  LÍMITE D7: "Rounding rules aceptables"
    • Válidos: ["none", "5min", "10min", "15min", "30min"]
    • Rechazar: ["1min", "2min", "7min", etc.]
    
    Si viola: Log "INVALID_ROUNDING_RULE"

BENEFICIO:
  ✓ Claridad sobre qué es "normal" vs "anomalía"
  ✓ Facilita validación de data entry
  ✓ Detección automática de configuración rota
  ✓ Base para alerting (cuando parámetros salen de rango)

2.1 CONCEPTOS QUE DEBERÍAN FORMALIZARSE
─────────────────────────────────────────

PROBLEMA:
  El código usa términos con múltiples significados:
  • "punch" = entrada en log ZKTeco (0,1,4,5,8,9)
  • "check-in" = primer punch de tipo entrada en rango
  • "block" = periodo de entrada/salida continuo
  • "obligation" = concepto en DayContext pero nunca usado
  • "payload data" = qué va en DailyAttendance pero no está documentado

PROPUESTA: GLOSARIO EJECUTABLE DE TÉRMINOS

  TÉRMINO T1: "Punch"
    Definición: Evento crudode asistencia registrado en dispositivo ZKTeco
    Atributos: timestamp, user_id, punch_state (0-9)
    Asignado a: models.AttendanceLog
    Valores válidos: 0,1,4,5,8,9 (otros valores => ignored or log warning)
    
    Conceptualmente: "una pulsación de botón en el dispositivo"

  TÉRMINO T2: "Check-in"
    Definición: PRIMER punch de tipo entrada [0, 4, 8] dentro de search_window
    Asignado a: DailyAttendance.check_in
    Invariantes:
      • check_in <= check_out (si check_out existe)
      • check_in >= search_start
      • check_in es ÚNICO (más no)
    
    Conceptualmente: "momento en que el empleado arriba"

  TÉRMINO T3: "Check-out"
    Definición: ÚLTIMO punch de tipo salida [1, 5, 9] dentro de search_window
    Asignado a: DailyAttendance.check_out
    Invariantes:
      • check_out >= check_in (si check_in existe)
      • check_out <= search_end
      • check_out es ÚNICO
    
    Conceptualmente: "momento en que el empleado se retira"

  TÉRMINO T4: "Block (en flexible schedule)"
    Definición: Período continuo de entrada-salida
    Composición: [check_in, check_out] pair
    Múltiple: Un flexible puede tener N blocks en un día
    Ejemplo: 09:00-12:00 bloque 1, 13:00-17:00 bloque 2
    
    Conceptualmente: "una jornada de trabajo sin interrupción"

  TÉRMINO T5: "Obligation (concepto arquitectónico)"
    Definición: Estado de si el empleado DEBE estar presente
    Valores: {TRUE, FALSE}
    Mapeado en DayContext.obligation
    Status actual: Casi siempre TRUE cuando is_valid=True, pero concepto subyacente
    
    Conceptualmente: "¿tiene este empleado una obligación contractual hoy?"
    Posible futuro: Leave, holiday, sabbatical => obligation=False

  TÉRMINO T6: "Payload Data"
    Definición: Datos de entrada para cálculo (no decisión, no meta)
    Composición:
      • Logs (list of AttendanceLog)
      • Timetable (schedule config)
      • Holidays (list of dates)
      • Leave info (boolean)
    Asignado a: ProcessorContext (V2), inline en V1
    
    Conceptualmente: "input crudo que alimenta el cálculo"

  TÉRMINO T7: "Decision Context"
    Definición: Datos que afectan CÓMO se calcula (no qué se calcula)
    Composición:
      • is_flexible (afecta processor selection)
      • rounding_rule (afecta check-in/out)
      • late_allow_minutes (afecta late calculation)
      • break_minutes (afecta worked calculation)
    Asignado a: Timetable (BD), DayContext (runtime)
    
    Conceptualmente: "parámetros de configuración del cálculo"

  TÉRMINO T8: "Offline-first Calculation"
    Definición: Cálculo que NUNCA depende de APIs externas en runtime
    Derivación: Todos los datos deben estar en BD pre-cálculo
    Garantía: calculate_day(emp_id, date) funciona con BD en "snap" histórico
    
    Conceptualmente: "puedo calcular asistencia sin conectividad"

BENEFICIO:
  ✓ Reduce ambigüedad en comunicación
  ✓ Facilita onboarding de nuevos devs
  ✓ Base para generar "Calculation Report" intelligible
  ✓ Previene confusiones entre "punch" vs "check-in"


2.2 ROLES ARQUITECTÓNICOS QUE NECESITAN VISIBILIDAD

PROBLEMA:
  Hoy V1 y V2 parecen "simétricos" sin documentación clara de roles.

      • Errores logueados pero absorbidos
    Ciclo de vida:
      • Producción: TODAY
      • Deprecación: NEVER (unless V2 proven 100%)

      • Recolecta evidencia para mayor cambio

      • Nunca afecta datos en BD (persist=False)
      • Failures nunca rompen V1
      • Cálculo paralelo => divergencia detectable

      • Producción: TODAY (shadow only)
      • Futura: Podría ser Autoridad (si V1 deprecado)
    
    Contrato:
      """
      def calculate_day_v2(emp_id: int, date: date, persist=False) -> DailyAttendance:
        # Precondición: emp_id existe, date es válida

        # Garantía: ShadowModeService puede comparar con V1

      • ÚNICA función de resolución de horario

      • Prioridad: OVERRIDE > EMPLOYEE > DEPARTMENT > IMPLICIT_REST

      • Determinística (siempre mismo resultado dado inputs)

3.2 DIFERENCIAS DE ESTADO: "CORRECTO" VS "SOSPECHOSO" VS "FALLO"
────────────────────────────────────────────────────────────────

PROBLEMA:
  Hoy un resultado de calculate_day() puede estar:
  • Correcto (sin issues)
  • Sospechoso (edge case, pero probablemente ok)
  • Fallido (error, pero atrapado)
  
  No hay manera de diferenciarlos sin leer logs linealmente.

PROPUESTA: CALCULATION_CONFIDENCE ENUM

  Crear métadato en DailyAttendance: calculation_confidence

  CONFIDENCE_LEVEL C1: "CERTAIN" (verde)
    Significado: Cálculo sin issues, procede como creemos
    Condiciones:
      • Todos los invariantes se cumplen
      • Ningún boundary condition se disparó
      • Logs encontrados en search window
      • is_flexible=False (fixed es "más estable")
    
    Ejemplo:
      emp=123, date=2026-02-10, status=Normal, confidence=CERTAIN
      => Confío en este resultado

  CONFIDENCE_LEVEL C2: "LIKELY" (amarillo)
    Significado: Cálculo plausible pero hay sospechas
    Condiciones:
      • Al menos un boundary condition se disparó (ej: B3 duplicate logs)
      • Invariantes ok
      • Pero resultado es potencialmente affected
    
    Ejemplo:
      emp=123, date=2026-02-10, status=Worked, confidence=LIKELY, boundary_hit=B3
      => Probablemente correcto, pero chequear si hay logs duplicados

  CONFIDENCE_LEVEL C3: "UNCERTAIN" (naranja)
    Significado: Cálculo completado pero hay warning
    Condiciones:
      • Invariante casi violada (ej: late_minutes=60, en límite)
      • Es flexible schedule con 0 logs (complejo)
      • Edge case poco frecuente activado
    
    Ejemplo:
      emp=123, date=2026-02-10, status=Incomplete, confidence=UNCERTAIN, reason=ZERO_LOGS_FLEXIBLE
      => Hecho correctamente pero revisa BD de logs

  CONFIDENCE_LEVEL C4: "FAILED" (rojo)
    Significado: Cálculo completado pero con fallback
    Condiciones:
      • Invariante VIOLADA (ej: negative worked_minutes)
      • Boundary fallido (ej: timetable=None pero is_valid=True)
      • Exception caught pero resultado es guess
    
    Ejemplo:
      emp=123, date=2026-02-10, status=Absent, confidence=FAILED, reason=TIMETABLE_LOST
      => Hecho fallback, revisa logs de error

CÓMO IMPLEMENTAR (SIN CÓDIGO):
  1. Agregar campo optional: calculation_confidence: Optional[str]
  2. En log de CALC_END, incluir: confidence=CONF_LEVEL
  3. En UI (future), mostrar icono verde/amarillo/naranja/rojo
  4. En API, permitir filter: ?min_confidence=LIKELY (excluye low confidence)
  5. En admin, crear dashboard: % de CERTAIN, LIKELY, UNCERTAIN, FAILED

BENEFICIO:
  ✓ Usuario sabe en qué confiar
  ✓ Admins saben dónde investigar
  ✓ Dashboard muestra health del sistema
  ✓ Facilita decisiones de "recompute"

4.1 RIESGOS HUMANOS Y CÓMO MITIGARLOS
──────────────────────────────────────

PROBLEMA:
  El core es código crítico pero sin protecciones contra uso incorrecto human:
  - Dev puede hacer "calculate_day_v2(persist=True)" por error en debug
  - Dev puede cambiar V1 sin revalidar contra V2
  - Dev puede agregar tolerancia a "100 minutos" sin validar
  - Dev puede confundir V1 (autoridad) con legacy

PROPUESTA: GUARDRAILS CONCEPTUALES (NO EXECUTABLE CODE)

  GUARDRAIL G1: "V2 persist=True es prohibido fuera de tests"
    Régimen:
      • Documentar explícitamente: "V2 NUNCA debe persistir en desarrollo"
      • En CI/CD: Assert no hay calls a calculate_day_v2(..., persist=True)
      • En code review: "¿persiste V2?" => reject unless test context
      • En docstring: """
        ADVERTENCIA: persist=True es SOLO para testing.
        En shadow mode, siempre usar persist=False.
        """
    Protección: Evita que V2 "contamine" BD con datos de shadow

  GUARDRAIL G2: "resolve_schedule_unified() es contrato sagrado"
    Régimen:
      • No modificar sin tests V1+V2 juntos
      • cambio => todos tests deben pasar
      • cambio => ShadowComparison debe matchear 100%
      • En docstring: """
        ADVERTENCIA: Esta función es usado por AMBOS engines.
        Un cambio aquí afecta V1 y V2 simultáneamente.
        Requerido: Test suite completa + shadow mode validation.
        """
    Protección: Evita divergencia involuntaria

  GUARDRAIL G3: "Domain limits no son "just numbers""
    Régimen:
      • Documentar RAZÓN de cada límite
      • late_allow_minutes <= 60
        => "RAZÓN: máximo realista es 1h gracia, >60min es error de cfg"
      • break_minutes <= 240
        => "RAZÓN: >4h de break es irreal, probablemente error de data"
      • En Timetable model: validators que rechacen out-of-range
    Protección: Evita "garbage in, garbage out"

  GUARDRAIL G4: "V1 NO es legacy, es autoridad"
    Régimen:
      • Comentario en code: "# AUTHORITY ENGINE V1"
      • Documentación: "V1 es oficial, V2 es validador"
      • Code review: Si alguien sugiere "deprecar V1", requiere explicación
      • En ADR: Decisión explícita de cuándo/cómo migrar
    Protección: Evita accidental removal o degradation

  GUARDRAIL G5: "Agregar lógica a ambos engines = riesgoso"
    Régimen:
      • Política: Agregr lógica a V1 PRIMERO siempre
      • Verificar invariantes después
      • Luego implementar en V2 DESPUÉS
      • Verificar ShadowComparison = MATCH
      • Solo entonces: commit ambos
      • En wiki: "Procedimiento para agregar features"
    Protección: Evita divergencia silenciosa

  GUARDRAIL G6: "Offline-first es garantía arquitectónica"
    Régimen:
      • Documentar: "calculate_day() usa SOLO datos en BD"
      • No permitir calls a APIs/Redis/etc en core

6.1 POR QUÉ NO CAMBIAR V1 HOY

    ✗ El objetivo de V1 es ser ESTABLE, no elegante
  
  Cuándo SÍ:
    • Después que V2 sea 100% probado (mínimo 3 meses)
    • ShadowComparison = 0 divergencias
    • Decisión ejecutiva: "V2 será nueva autoridad"
    • PERO ANTES: Mantener V1 como shadow (para fallback)


CAMBIO NR2: "Eliminar duplicación entre V1 y V2"
  Por qué NO:
    ✗ "deuda técnica" es mejor que "riesgo operacional"
    ✗ Un engine es "insurance" del otro
    ✗ Si unifico y doy error => ambos roto
    ✗ No es código legacy, es código intencional
  
  Cuándo SÍ:
    • Nunca. La duplicación ES el diseño.
    • Máximo: extender ambos simultáneamente (V1, luego V2)


CAMBIO NR3: "Agregar "inteligencia" con ML/IA"
  Por qué NO:
    ✗ Sistema debe ser determinístico (offline-first)
    ✗ ML introducing no-determinism
    ✗ Auditoría regulatoria => no se permiten "blackboxes"
    ✗ "¿Por qué status=Late?" debe ser explicable (regla, no ML)
  
  Cuándo SÍ:
    • Nunca en el core del cálculo
    • Sí podría usarse en: anomaly detection (POST-cálculo)


CAMBIO NR4: "Convertir en CRM / agregar workflows / tasks"
  Por qué NO:
    ✗ Sistema hoy es pure CALCULATION (no proceso)
    ✗ Agregar workflow = agregar state machines, lado effects
    ✗ Si hago calculate_day() y dispara "cambiar estado empleado", roto determinismo
    ✗ El propósito HOY es: mostrar información
  
  Cuándo SÍ:

    • Crear servicio SEPARADO: human_processes.py
    • Que consume DailyAttendance pero NO modifica calculate_day()


CAMBIO NR5: "Optimizar BD queries agresivamente"
  Por qué NO:
    ✗ Cálculo es batch (no OLTP tiempo real)
    ✗ Premature optimization mata claridad
    ✗ Risk: Agregar índices mal => queries lentas
    ✗ mejor opción: Cache en application layer si es problema
  
  Cuándo SÍ:

  Cuándo SÍ:

    ✗ Si algo rompe, ambos rompe (no hay fallback)
