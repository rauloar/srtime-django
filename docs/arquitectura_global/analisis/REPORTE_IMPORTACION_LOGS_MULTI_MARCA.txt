2.2 PROBLEMA CENTRAL: "PUNCH CODE SEMANTIC" (CRÍTICO)
──────────────────────────────────────────────────────

LA CUESTIÓN:

  ZKTeco: punch=0 → Check-in, punch=1 → Check-out
  HIKVISION: event_type="IN", event_type="OUT"
  CSV file: action="entrada", action="salida"
  TXT file: 1,0 → entrada/salida alternada
  
  CORE consume atacando .punch como IntegerField (0-9)
  CORE no entiende diferencia semántica entre:
    punch=0 (is it IN? OUT? BREAK?)


CÓMO FUNCIONA HOY SIN ROMPER:

  El CORE (en flexible vs fixed) probablemente hace:

    1. Ordena logs por timestamp
    2. Agrupa punches en PARES (1er punch = entrada, 2do = salida)
    3. Calcula duración = salida - entrada

  Esto FUNCIONA porque:
    • Asume alternancia: IN, OUT, IN, OUT
    • No importa si punch=0 o punch=1 (solo cuenta orden)
    • Es AGNÓSTICO a códigos


IMPLICACIÓN:

  ✓ El CORE es resiliente
  ✓ No necesita cambiar punch si mantenemos pares ordenados
  ✗ Pero: Pierde semántica (no sabe qué es cada código)
  ✗ Y: Si hay eventos especiales (BREAK, LUNCH), se rompe


SOLUCIÓN: Agregar campo normalized_punch_type

  Nuevo campo:
    normalized_punch_type: CharField(choices=[
      'IN',           # Check-in / Entrada
      'OUT',          # Check-out / Salida
      'BREAK_OUT',    # Salida a descanso
      'BREAK_IN',     # Entrada de descanso
      'LUNCH_OUT',    # Salida a almuerzo
      'LUNCH_IN',     # Entrada de almuerzo
      'SPECIAL'       # Evento especial sin mapeo
    ])

  Mantener punch original para debugging
  Usar normalized_punch_type para lógica

3.1 CONCEPTO: "TRAVEL DOCUMENT" PARA CADA LOG
───────────────────────────────────────────────

Propuesta arquitectónica:

Antes de insertar en DB, cada log debe pasar por NORMALIZACIÓN.

LA IDEA:

  Archivo TXT/CSV/Raw
    ↓ (Parser específico)
  Raw Event Object
    ├─ text: "2026-02-10 09:15 EMP123 IN"
    └─ source: "txt_file"
    ↓ (Adapter/Normalizer)
  Normalized Event
    ├─ user_id: "EMP123"
    ├─ timestamp: datetime(2026, 2, 10, 9, 15)
    ├─ punch: 0 (ó mantener NULL si no es ZKTeco)
    ├─ normalized_punch_type: "IN"
    ├─ source_system: "txt_upload"
    ├─ device_id: "UNKNOWN" (ó detectado)
    └─ other fields: ...
    ↓ (Validation)
  Validated Event
    ├─ ✓ timestamp es válido
    ├─ ✓ user_id existe en BD
    ├─ ✓ no es duplicate
    └─ ✓ no quebranta invariantes
    ↓ (Insert)
  AttendanceLog record en BD


INVARIANTES QUE DEBE CUMPLIR:

  I1: user_id EXISTE en BD (Employee table)
      Razón: CORE hace .filter(user_id=X)
      
  I2: timestamp es timezone-aware
      Razón: CORE compara con dates
      
  I3: normalized_punch_type es válido
      Razón: Lógica futura puede usarlo
      
  I4: No hay duplicado (user_id, timestamp) en mismo batch
      Razón: Eso sería error en importación
      
  I5: timestamp >> imported_at NO es cierto
      (Log no puede ser del futuro respecto a importación)

3.3 ALGORITMO DE NORMALIZACIÓN (PSEUDOCÓDIGO)

def normalize_event(raw_event, source_system):
    """
    Transforma raw_event → AttendanceLog object (no persiste aún)
    """
    
    # PASO 1: Parse / Extract
    if source_system == 'zkteco':
        user_id = raw_event.user_id  # asume ya está parsed por pyzk
        timestamp = raw_event.timestamp
        punch_code = raw_event.punch  # 0, 1, 2, 3, ...
        device_id = raw_event.device_id
        external_event_id = None
        
    elif source_system == 'csv':
        user_id = raw_event['emp_id']
        timestamp = parse_datetime(raw_event['date'] + ' ' + raw_event['time'])
        punch_code = map_action_to_code(raw_event['action'])  # IN→0, OUT→1
        device_id = raw_event.get('device', device_id_from_code(raw_event['code']))
        external_event_id = hash_event(user_id, timestamp, action)
        
    elif source_system == 'txt':
        user_id, timestamp, action = parse_txt_line(raw_event)
        punch_code = map_action_to_code(action)
        device_id = detect_device_from_context()
        external_event_id = hash_event(user_id, timestamp, line_number)
        
    elif source_system == 'raw_ascii':
        user_id, timestamp, action = smart_parse(raw_event)
        punch_code = map_action_to_code(action)
        device_id = 'UNKNOWN'
        external_event_id = hash_event(user_id, timestamp, position)
    
    # PASO 2: Mapear punch code a tipo normalizado
    normalized_type = punch_code_to_normalized(punch_code, source_system)
    # 0→IN, 1→OUT, 2→BREAK_OUT, 3→BREAK_IN, etc.
    
    # PASO 3: Validar invariantes
    assert Employee.objects.filter(user_id=user_id).exists(),
        f"user_id {user_id} not found"
    
    assert timestamp is not None,
        "timestamp missing"
    
    assert normalized_type in VALID_TYPES,
        f"unknown punch type: {normalized_type}"
    
    # PASO 4: Crear objeto (no persiste)
    normalized = {
        'user_id': user_id,
        'timestamp': timestamp,
        'punch': punch_code,  # Mantener para debugging
        'normalized_punch_type': normalized_type,
        'device_id': device_id,
        'source_system': source_system,
        'source_format': source_system + '_v1',
        'external_event_id': external_event_id,
        'imported_at': now(),
        'import_batch_id': batch_id,
        # ZKTeco fields (null para otros)
        'verify_type': raw_event.get('verify_type', None),
        'status': raw_event.get('status', None),
        'reserved': raw_event.get('reserved', None),
    }
    
    return normalized

4.2 COMPONENTES CLAVE
──────────────────────

COMPONENTE 1: Importer Base Class

  Responsabilidades:
    ✓ Definir interfaz común
    ✓ Validators hook
    ✓ Norms hook
    ✓ Reporting hook
    
  NO responsable de:
    ✗ Lógica de cálculo (CORE)
    ✗ Decisiones de negocio
    ✗ Transformaciones complejas
    
  Pseudo-interface:
    
    class BaseImporter:
        def __init__(self, batch_id, source_system):
            self.batch_id = batch_id
            self.source_system = source_system
            
        def parse(self) -> List[RawEvent]:
            """Lee source, retorna raw events"""
            raise NotImplementedError
            
        def normalize(self, raw_events) -> List[NormalizedEvent]:
            """Transforma a forma normal"""
            return [self.normalizer.normalize(e) for e in raw_events]
            
        def validate(self, events) -> (List[Valid], List[Invalid]):
            """Valida invariantes"""
            return self.validator.validate(events)
            
        def import_(self, valid_events) -> ImportResult:
            """Persiste a BD"""
            return self.db_service.bulk_insert(valid_events)
            
        def report(self) -> ImportReport:
            """Estadísticas del import"""
            return {
                'total': N,
                'imported': N-X,
                'rejected': X,
                'reasons': [...],
                'batch_id': self.batch_id
            }


COMPONENTE 2: Parser (Lee la fuente)

  Responsabilidades:
    ✓ Detectar formato automáticamente (si es posible)
    ✓ Leer línea por línea o chunk por chunk
    ✓ Extraer campos crudos
    ✓ Crear RawEvent objects
    
  Ejemplos:
    
    CSVParser:
      ├─ Lee CSV con detectar delimitador si es posible
      ├─ Mapea columnas a RawEvent schema
      ├─ Retorna List[RawEvent]
      └─ Maneja encoding errors (UTF-8, Latin-1, etc.)
      
    TXTParser:
      ├─ Lee línea por línea
      ├─ Detecta patrón (pipe, tab, space)
      ├─ Regex matching para user_id, timestamp
      ├─ Retorna List[RawEvent]
      └─ Logs parse errors por línea
      
    RawASCIIParser:
      ├─ Smart detection de formato
      ├─ Intenta patrones comunes
      ├─ Fallback a genérico si falla
      ├─ Retorna List[RawEvent]
      └─ Notas de baja confianza


COMPONENTE 3: Adapter (Mapea Brand-specific → Universal)

  Responsabilidades:
    ✓ Traducir códigos específicos de marca
    ✓ Mapear campos de origen a universal
    ✓ Manejar variaciones de formato
    
  Ejemplos:
    
    ZKTecoAdapter:
      ├─ punch: 0→IN, 1→OUT, 2→BREAK_OUT
      ├─ status, verify_type → mantiene (ZKTeco-specific)
      ├─ timestamp → tz-aware
      └─ device_id → del Device del sistema

    def validate(events) -> (valid, invalid):
        valid = []
        invalid = []
        
        for event in events:
            errors = []

            if not Employee.objects.filter(
                user_id=event['user_id']
            ).exists():
                errors.append(f"user_id {event['user_id']} not found")
                
            # Check I2: timestamp valid
            if event['timestamp'] is None:
                errors.append("timestamp missing")
                
            # Check I3: type valid
            if event['normalized_punch_type'] not in VALID_TYPES:
                errors.append(f"invalid type: {event['normalized_punch_type']}")

                errors.append("timestamp is from future")
                
            if errors:
                invalid.append({
                    'event': event,
                    'errors': errors
                })
            else:
                valid.append(event)
                
        return valid, invalid

5.2 MANEJO DE ERRORES EN IMPORTACIÓN
─────────────────────────────────────

ESCENARIO E1: Archivo malformado (encoding)
  ├─ Síntoma: Línea no se puede parsear
  ├─ Detección: Try/except en parser
  ├─ Acción: Log línea, continear (rolling)
  ├─ Reporte: "Line 42: encoding error (expected UTF-8)"
  └─ Resultado: Registro se rechaza (no se inserta)

ESCENARIO E2: user_id no existe
  ├─ Síntoma: Employee.objects.filter(user_id='NOTEXIST')
  ├─ Detección: En validador
  ├─ Acción: Add a invalid list, continua
  ├─ Reporte: "EMP_ID ABC123 not found in system"
  └─ Resultado: Registro se rechaza

ESCENARIO E3: Timestamp inválido
  ├─ Síntoma: datetime.fromisoformat() raises ValueError
  ├─ Detección: En parser o normalizer
  ├─ Acción: Log error, marcar como inválido
  ├─ Reporte: "Row 15: invalid timestamp '32:99:00' ← invalid hour"
  └─ Resultado: Registro se rechaza

ESCENARIO E4: Duplicado dentro del batch
  ├─ Síntoma: Dos eventos (user_id, timestamp) idénticos en misma importación
  ├─ Detección: Hash set en validador
  ├─ Acción: Marcar segundo como inválido (keep first)
  ├─ Reporte: "Row 100: duplicate (EMP001, 2026-02-10T09:15)"
  └─ Resultado: Uno se rechaza

ESCENARIO E5: Duplicado en BD (reintentar import)
  ├─ Síntoma: (user_id, timestamp) ya existe en BD
  ├─ Detección: DB constraint ó validador pre-insert
  ├─ Acción: Opción A: Ignorar (idempotente), Opción B: Fail fast
  ├─ Reporte: "Row 50: already in DB (EMP002, 2026-02-08T14:30)"
  └─ Resultado: Depende de configuración (upsert vs skip)

ESCENARIO E6: Transaction rollback
  ├─ Síntoma: DB error en insert (disk full, constraint, etc.)
  ├─ Detección: Exception durante bulk_insert
  ├─ Acción: Rollback TODO el batch
  ├─ Reporte: "Import failed: PostgreSQL constraint violation"
  └─ Resultado: NINGÚN registro se inserta


FILOSOFÍA DE ERRORES:

  ✓ Fail soft (continue on validation errors)
  ✓ Fail hard (stop on DB errors)
  ✓ Report all (cada rechazo es logged)
  ✓ Rollback batch (si transaction falla, borra el batch)


5.3 IDEMPOTENCIA (Reintentar dedesde del principio)
────────────────────────────────────────────────────

PROBLEMA: ¿Qué pasa si usuario reintenta upload del mismo archivo?

SOLUCIÓN: external_event_id

  El import crea unique constraint en:
    (user_id, timestamp, import_batch_id, external_event_id)
  
  Reintentoar con MISMO BATCH_ID:
    ├─ Primer intento: inserta 1500 registros
    ├─ Segundo intento: detecta external_event_ids idénticos
    ├─ Acción: UPDATE o SKIP (configurable)
    └─ Resultado: Idempotente (1500, no 3000)

  Reintentos con BATCH_ID DIFERENTE:
    ├─ Se usa nuevo batch_id
    ├─ external_event_id mismo
    ├─ Constraint: puede ser un problema si es unique global
    ├─ Solución: unique es (source_system, external_event_id, user_id, timestamp)
    └─ Resultado: Detecta duplicados de cualquier batch


RECOMENDACIÓN:
  ✓ external_event_id DEBE ser unique + db_index
  ✓ Operación de re-upload intenta UPDATE
  ✓ Mantiene auditoría (modified_at, updated_by)

10. COSAS QUE NO HACER TODAVÍA  (Explícito Out-of-Scope)
================================================================================

❌ NO agregar lógica de cálculo dentro de importación
  Razón: CORE es caja negra, importación es pura prep

❌ NO crear "workflow de aprobación de logs"
  Razón: Sistema es informativo, no CRM

❌ NO soportar "edición de logs post-import"
  Razón: Rompe auditoría, complica migración V1→V2

❌ NO crear "reconciliación automática" entre dispositivos
  Razón: Requiere reglas de negocio (HR decision)

❌ NO hacer real-time streaming desde dispositivos
  Razón: Importación es offline-first por diseño

❌ NO soportar "partial updates" de batches
  Razón: Transactionalidad es todo-o-nada

❌ NO crear "histórico de cambios" a log individual
  Razón: Amplía modelo sin valor inmediato

❌ NO tocar resolve_schedule_unified() o lógica V1/V2
  Razón: CORE stays intact

❌ NO hacer migraciones de datos complejas antes de P2
  Razón: Primero estabilizar infraestructura

11.1 PREGUNTA 1: ¿Es posible convertirse en importador universal?
─────────────────────────────────────────────────────────────────

✅ SÍ, ES POSIBLE

Hoy:  Sistema es ZKTeco-centric (pyzk hardcoded)
Meta: Sistema agnóstico a marca, consume AttendanceLog normalizado

Cambios necesarios:
  • Modelo: +6 campos (no-breaking)
  • Arquitectura: Nueva capa de importers/ (sin tocar CORE)
  • Testing: Test suite exhaustiva
  • Esfuerzo: 9-11 semanas (1 team)

CORE permanece intacto: ✓ (caja negra garantizada)


11.2 PREGUNTA 2: ¿Se puede hacer offline?
───────────────────────────────────────────

✅ SÍ, ES OFFLINE-FIRST POR DISEÑO

Toda importación es:
  • De archivo local (TXT, CSV, etc.)
  • O de string pasado en request
  • Sin dependencias de APIs externas

Única excepción: ZKTeco legacy (si viene vía API), pero eso es HOY.
Nuevo stack: Archivo → Local import → DB.


11.3 PREGUNTA 3: ¿Se reutiliza CORE sin cambios?
──────────────────────────────────────────────────

✅ SÍ, 0 MODIFICACIONES A V1 O V2

El CORE:
  • Sigue consumiendo AttendanceLog como hoy
  • Sigue usando punch field (valores pueden ser cualquier int)
  • Sigue agnóstico a source_system
  • Sigue determinístico

Lo nuevo (normalized_punch_type) es para LÓGICA FUTURA, no necesario hoy.


11.4 PREGUNTA 4: ¿Qué fallaba del diseño ZKTeco?
──────────────────────────────────────────────────

Hoy: AttendanceLog es "ZKTeco-flavored"
  ├─ Campos como verify_type, status → ZKTeco específicos
  ├─ punch semántica es ZKTeco (0-9)
  ├─ Sin trazabilidad (source_system)
  ├─ Sin deduplicación (external_event_id)
  └─ Acoplez a pyzk library

Propuesta: AttendanceLog es "universal carrier"
  ├─ Mantiene datos crudos (punch original)
  ├─ Agrega metadatos de origen
  ├─ Mapea semanticamente (normalized_punch_type)
  ├─ Traceable (source_system, import_batch_id)
  └─ Desacoplado de pyzk (adapters layer)


11.5 PREGUNTA 5: ¿Riesgo para datos históricos?
────────────────────────────────────────────────

✅ RIESGO BAJO, MITIGABLE

Datos ZKTeco existentes:
  • No se modifican
  • Se setean defaults automáticamente en migration
  • source_system='zkteco_legacy'
  • normalized_punch_type detectada automáticamente (0→IN, 1→OUT)
  • V1 y V2 siguen calculando igual (retroactive test)

ShadowComparison post-migration:
  • DEBE retornar 0 divergencias
  • Si diverge: CRÍTICO (investigación)
  • Rollback posible si falla


11.6 PREGUNTA 6: ¿Y si usuario quiere agregar Hikvision?
────────────────────────────────────────────────────────

✅ TRIVIAL, SIN TOCAR CORE

Hikvision = CSV + Adapter:
  1. Exporta datos a CSV (estándar)
  2. Sube vía import UI
  3. Sistema auto-detects o user selecciona "CSV_Hikvision"
  4. Adapter mapea: access_type→normalized_punch_type
  5. Listo

Esfuerzo: 1-2 días (si formato conocido)
Riesgo: BAJO (architecture soporta extensión)
