1. RESUMEN FUNCIONAL DEL SISTEMA
================================================================================

SRTime Django es un SISTEMA DE GESTIÓN DE ASISTENCIA LABORAL basado en 
dispositivos ZKTeco (biometría) + cálculo de matemático de horas trabajadas.

QUÉ HACE:
• Ingesta raw de marcaciones biométricas (check-in / check-out) desde dispositivos
• Cálculo automático de métricas diarias por empleado (worked_minutes, late, early, overtime)
• Aplicación de reglas: schedule resolution, flexible vs fixed hours, late allowance
• Visualización de logs, reportes, y gestión de configuración de horarios
• Operaciones en dispositivos: importar, limpiar, sincronizar usuarios

QUÉ NO HACE:
• No genera nóminas ni retribuciones
• No integra con RR.HH externo
• No hace forecasting ni predicciones
• No maneja aprobaciones de licencias (solo almacenamiento)
• No es real-time (calcula en batch por período)

MODELO DE OPERACIÓN:
  1. Dispositivo ZKTeco registra marcaciones → Device local
  2. Sistema importa logs a AttendanceLog (raw: ts, user_id, status, punch)
  3. Usuario ejecuta cálculo en período (start_date → end_date)
  4. Engine resuelve horarios (override > shift > default) e calcula métricas
  5. DailyAttendance guardados (estado: Normal, Late, Absent, Leave, etc.)
  6. Frontend visualiza logs, reportes, y permite ediciones manuales

2. CASOS DE USO PRINCIPALES (END-TO-END)
================================================================================

FLUJO PRINCIPAL: INGESTA Y CÁLCULO DE ASISTENCIA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Caso 1: IMPORTAR MARCACIONES DE DISPOSITIVO
  Entrada: Usuario selecciona dispositivo en UI → Devices → Device Detail
  Acción: Click "Importar Marcaciones"
  Backend:
    POST /api/v1/devices/{id}/import-attendance/
    → pyzk.get_attendance() → AttendanceLog bulk create
    → Retorna Job(async) con status "running"
  Salida: Logs importados en BD (tabla AttendanceLog)
  UI actualiza: "✓ X marcaciones importadas"

Caso 2: CALCULAR ASISTENCIA EN PERÍODO
  Entrada: Usuario va a Attendance → Calculation
  Acción: Selecciona fecha inicio, fin, departmento (opcional) → "Calcular"
  Backend:
    POST /api/v1/attendance/calculate/
    Body: { "start_date": "2026-02-01", "end_date": "2026-02-07", "department_id": null }
    → Para cada empleado + fecha:
      1. resolve_schedule_unified(employee_id, date) → Timetable
      2. calculate_day(employee, date, timetable) → metrics
      3. DailyAttendance.save()
    → Retorna: { "processed_records": X, "skipped_employees": Y, ... }
  Salida: DailyAttendance con status (Normal/Late/Early/Absent/Leave/Incomplete)
  UI muestra: Resumen de cálculo, employees procesados, excepciones

Caso 3: VER REPORTES DE ASISTENCIA
  Entrada: Usuario va a Attendance → Reports
  Acción: Selecciona período → "Ver Reportes"
  Backend:
    GET /api/v1/daily-attendance/?date__gte=...&date__lte=...
    → Retorna array de DailyAttendance con métricas
  UI renderiza: Tabla empleado × día con status, minutos trabajados, etc.

Caso 4: EDITAR LOG MANUAL
  Entrada: Usuario ve log en Attendance → Logs → Edit
  Acción: Modifica check_in, check_out, guarda cambios
  Backend:
    PUT /api/v1/attendance-logs/{id}/
    Body: { "timestamp": "...", "edited_by": "admin", "edited_reason": "Device offline", "is_manual": true }
    → AttendanceLog.save() con audit trail
  Salida: Log editado, auditoría registrada
  UI: Toast "✓ Log actualizado"


FLUJO OPERACIONAL: GESTIÓN DE CONFIGURACIÓN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Caso 5: CREAR HORARIO
  Entrada: Usuario va a Personnel → Timetables → "Nuevo"
  Acción: Ingresa on_duty_time (09:00), off_duty_time (17:00), breaks, etc.
  Backend:
    POST /api/v1/timetables/
    Body: { "name": "9-5 Fijo", "on_duty_time": "09:00:00", ... }
    → Timetable.save()
  Salida: Horario guardado, ID retornado

Caso 6: CREAR TURNO Y ASIGNAR HORARIOS
  Entrada: Usuario va a Personnel → Shifts → "Nuevo"
  Acción: Ingresa nombre "Morning" → "Agregar Horarios por día"
  Backend:
    POST /api/v1/shifts/
    Body: { "name": "Morning", "cycle_days": 0 }
    → Shift.save() → ID retornado
    
    POST /api/v1/shift-timetables/
    Body: { "shift": shift_id, "timetable": timetable_id, "day_index": 0 }  # Lunes
    → ShiftTimetable.save() para cada día
  Salida: Turno con horarios por día creado

Caso 7: ASIGNAR TURNO A EMPLEADO
  Entrada: Usuario va a Personnel → Employees → Empleado → "Asignar Turno"
  Acción: Selecciona turno, fecha inicio → "Guardar"
  Backend:
    POST /api/v1/employee-shifts/
    Body: { "scope": "EMPLOYEE", "employee": emp_id, "shift": shift_id, "start_date": "2026-02-01" }
    → EmployeeShift.save()
  Salida: Asignación guardada, próximos cálculos usan este horario

Caso 8: EXCEPTIONS / SCHEDULE OVERRIDE
  Entrada: Usuario edita empleado → "Fecha Excepcional (Hoy)"
  Acción: Selecciona new timetable para hoy → "Guardar"
  Backend:
    POST /api/v1/schedule-overrides/
    Body: { "employee": emp_id, "date": "2026-02-10", "timetable": timetable_id }
    → ScheduleOverride.save()
  Salida: Horario override guardado
  Efecto: Próximo cálculo en esta fecha usa override en lugar de shift/departamento


FLUJO ADMINISTRATIVO: OPERACIONES EN DISPOSITIVOS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Caso 9: TEST DE CONEXIÓN
  Acción: Usuario va a Devices → Device Detail → "Test Conexión"
  Backend:
    POST /api/v1/devices/{id}/test-connection/
    → pyzk.connect() + ping básico → Job async
    → Retorna { "success": true/false, "message": "Connected" }
  UI: Muestra estado (Online/Offline) con indicador visual

Caso 10: DESCARGA DE USUARIOS
  Acción: Usuario va a Devices → "Descargar Usuarios"
  Backend:
    POST /api/v1/devices/{id}/download-users/
    → pyzk.download_users() → User table
    → JobLog: "Downloaded 28 users"
  Salida: Tabla User con info de dispositivo

4.2 SERVICIOS CRÍTICOS Y RESPONSABILIDADES
────────────────────────────────────────────

schedule_resolver.py (CRÍTICO)
  Responsabilidad única: Resolver qué horario tiene un empleado en una fecha
  Entrada: employee_id, date
  Proceso:
    1. Buscar ScheduleOverride(employee, date) → más prioritario
    2. Buscar EmployeeShift(scope='EMPLOYEE', employee) → prioridad media
    3. Buscar EmployeeShift(scope='DEPARTMENT', department) → fallback
    4. Si nada, retorna IMPLICIT_REST (no tiene horario = día libre)
  Salida: ResolvedSchedule(timetable, source, is_valid)
  Usado por: Como precondición en attendance_engine.calculate_day()
  Nota: Ambos engines (V1 y V2) usan la MISMA función (garantiza consistencia)

attendance_engine.py (CRÍTICO)
  Responsabilidad: Calcular métricas dinarias de asistencia
  Entrada: employee, date, timetable (ya resuelto)
  Proceso:
    1. Buscar AttendanceLog (device, user_id, fecha) → check_in, check_out
    2. Si no hay logs → status = "Absent"
    3. Si hay logs:
       a. Aplicar rounding rules (según timetable.rounding_rule)
       b. Calcular duración bruta: checkout - checkin
       c. Restar break_minutes
       d. Comparar con on_duty_time, off_duty_time
       e. Calcular discrepancias: late_minutes, early_minutes
       f. Calcular: worked_minutes = duración - breaks
       g. Calcular overtime_minutes = max(0, worked - required)
       h. Determinar status (Normal, Late, Early, Incomplete, Excessive)
    4. Guardar DailyAttendance con métricas
  Salida: DailyAttendance (status, worked_minutes, late_minutes, etc.)
  Nota: Cálculo determinístico — mismo input = mismo output

zk.py (CRÍTICO para INTEGRACIÓN)
  Responsabilidad: Comunicar con dispositivos ZKTeco vía pyzk
  Funciones:
    • connect(ip, port, password) → conexión socket
    • get_attendance() → fetch logs desde dispositivo
    • download_users() → descargar registro de usuarios
    • sync_users(employees) → pusha usuarios a dispositivo
    • device operations: restart, poweroff, sync_time, test_voice
  Tipo de operación: SÍNCRONA (blocking TCP)
  Timeout: Por defecto en pyzk (~10s)
  Manejo de errores: Básico (puede lanzar excepciones)

jobs.py
  Responsabilidad: Gestionar trabajos (abstracción para operaciones async)
  Funciones:
    • create_job(type, device_id) → Job(status='pending')
    • start_job(job_id) → Job(status='running', started_at=now)
    • finish_job(job_id, status, error) → completar
    • set_progress(job_id, %) → actualizar progreso
    • append_log(job_id, message) → registro de paso a paso
  Nota: "Async" en abstracción, pero implementación SÍNCRONA (no Celery)
  Efecto: Operaciones largas (import attendance, download users) bloquean
  Workaround en DEV: Aceptable porque usuarios son pocos

5. ATTENDANCE ENGINE — FLUJO DE CÁLCULO DETALLADO
================================================================================

ENTRADA MÍNIMA:
  employee_id: 123
  date: 2026-02-10 (datetime.date)
  
PASO 1: RESOLVER HORARIO
  ├─ resolve_schedule_unified(123, 2026-02-10)
  │  ├─ Check ScheduleOverride(emp=123, date=2026-02-10) → None
  │  ├─ Check EmployeeShift(scope='EMPLOYEE', emp=123)
  │  │  → Found: Shift "Morning" starting 2026-02-01
  │  ├─ Resolve shift → ShiftTimetable(shift=..., day_index=0) [Lunes]
  │  │  → Timetable: "9-5 Fixed"
  │  │    • on_duty_time: "09:00:00"
  │  │    • off_duty_time: "17:00:00"
  │    • break_minutes: 60
  │    • late_allow_minutes: 10
  │    • rounding_rule: "none"
  │  └─ RETURN: ResolvedSchedule(timetable=Timetable(...), source='EMPLOYEE_SHIFT')

PASO 2: BUSCAR LOGS DEL DÍA
  ├─ AttendanceLog.objects.filter(
  │    device__employee__user_id=emp.user_id,
  │    date__date='2026-02-10'
  │  ).order_by('timestamp')
  │  → [
  │      AttendanceLog(user_id='EMP001', timestamp='2026-02-10 08:45:00', status=0, punch=0),
  │      AttendanceLog(user_id='EMP001', timestamp='2026-02-10 17:05:00', status=0, punch=1)
  │    ]

PASO 3: VALIDAR QUE HAY LOGS
  ├─ if not logs:
  │    return DailyAttendance(status='Absent', worked_minutes=0, ...)
  └─ Continuamos...

PASO 4: EXTRAER TIMESTAMPS
  ├─ check_in = 08:45:00 (primer punch=0)
  └─ check_out = 17:05:00 (último punch=1)

PASO 5: APLICAR ROUNDING (si aplica)
  ├─ rounding_rule = "none" → sin cambios
  │  (otros: "5min", "10min", etc. → redondean hacia arriba/abajo)
  └─ check_in = 08:45:00, check_out = 17:05:00

PASO 6: CALCULAR DURACIÓN BRUTA
  ├─ duration = 17:05:00 - 08:45:00 = 8 horas 20 minutos = 500 minutos

PASO 7: RESTAR BREAKS
  ├─ break_minutes = 60 (configurado)
  ├─ net_worked = 500 - 60 = 440 minutos

PASO 8: BUSCAR HORARIO ESPERADO
  ├─ on_duty = 09:00:00
  └─ off_duty = 17:00:00
  ├─ expected_duration = 17:00 - 09:00 = 8 horas = 480 minutos

PASO 9: CALCULAR DISCREPANCIAS
  ├─ late_minutes = max(0, on_duty - check_in)
  │  = max(0, 09:00 - 08:45) = 0 (NO llegó tarde)
  │
  ├─ early_minutes = max(0, check_out - off_duty)
  │  = max(0, 17:05 - 17:00) = 5 (Salió 5 minutos tarde)
  │
  └─ Nota: Si llegó DESPUÉS de on_duty:
     late_minutes = check_in - on_duty (en minutos)

PASO 10: CALCULAR OVERTIME
  ├─ required_minutes = 480 (de Timetable.required_minutes o inferido)
  ├─ worked_minutes = net_worked = 440 (o mayor si trabajó más)
  └─ overtime_minutes = max(0, worked_minutes - required)
     = max(0, 440 - 480) = 0 (trabajó MENOS)

PASO 11: APLICAR TOLERANCIAS
  ├─ late_allow_minutes = 10 (configurado)
  ├─ if late_minutes <= late_allow_minutes:
  │    late_minutes = 0 (se perdona)
  │
  └─ early_leave_allow_minutes = 10 (configurado)
     if early_minutes <= early_leave_allow_minutes:
       early_minutes = 0 (se perdona)

PASO 12: DETERMINAR STATUS
  ├─ rules (en orden de evaluación):
  │  1. if leave exists → status = 'Leave'
  │  2. if holiday AND (checked_in) → status = 'HolidayWorked'
  │  3. if not check_in AND not check_out → status = 'Absent'
  │  4. if late_minutes > 0 → status = 'Late'
  │  5. if early_minutes > 0 AND worked < required → status = 'Early'
  │  6. if worked > (required * 1.5) → status = 'Excessive'
  │  7. if worked >= required → status = 'Normal'
  │  8. else → status = 'Incomplete'
  │
  └─ En este ejemplo: status = 'Incomplete' (trabajó 440 < 480 requeridos)

PASO 13: GUARDAR
  ├─ DailyAttendance.objects.create(
  │    employee=emp,
  │    date='2026-02-10',
  │    check_in=datetime(2026, 2, 10, 8, 45),
  │    check_out=datetime(2026, 2, 10, 17, 5),
  │    on_duty='09:00:00',
  │    off_duty='17:00:00',
  │    late_minutes=0,
  │    early_minutes=0,
  │    worked_minutes=440,
  │    overtime_minutes=0,
  │    status='Incomplete',
  │    exception_reason=None,
  │    timetable=timetable
  │  )

SALIDA:
  DailyAttendance(
    employee_id=123,
    date=2026-02-10,
    status='Incomplete',
    worked_minutes=440,
    late_minutes=0,
    overtime_minutes=0
  )

    const API_URL = import.meta.env.VITE_API_BASE_URL || 'http://127.0.0.1:9000/api/v1'
    api.interceptors.request.use(config => {
      const token = sessionStorage.getItem('auth_token')

      return config
    })
