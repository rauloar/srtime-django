FASE 3: ANÁLISIS DETALLADO DE IDEMPOTENCIA (✅ HALLAZGOS CRÍTICOS)
================================================================================

DEFINICIÓN de Idempotencia:
  "Aplicar la misma operación múltiples veces = mismo resultado que aplicarla una sola vez"
  Para ingesta de datos: Re-importar mismo archivo debería resultar en CERO cambios (segundas instancia)

VECTOR 1: zk_workers.py:run_import_attendance_job() - PRODUCCIÓN

  OPERATIVA ACTUAL:
    ```
    for att in records:  # Records from pyzk.get_attendance()
        exists = AttendanceLog.objects.filter(
            device_id=device_id,
            user_id=att.user_id,
            timestamp=att.timestamp
        ).exists()  ← Query con index (device, user_id, timestamp)
        
        if exists and not overwrite:
            skipped_count += 1
            continue
        
        if overwrite and exists:
            AttendanceLog.objects.filter(...).update(status, punch, verify_mode)
        else:
            AttendanceLog.objects.create(device_id, user_id, timestamp, ...)
        
        imported_count += 1
    ```
  
  IDEMPOTENCIA CHECK:
    ✓ Primera ejecución:
      - Records quedan en BD
      - imported_count = X, skipped_count = 0
    
    ✓ Segunda ejecución (overwrite=False, mismo records):
      - .exists() devuelve True para todos
      - Todos son skipped
      - imported_count = 0, skipped_count = X
    
    ✓ Resultado: Idempotent (mismos registros al final)
  
  ⚠️ CAVEAT - RACE CONDITIONS:
    - NO transaction.atomic() → Partial imports posible si falla a mitad
    - Entre .exists() check y .create(): Otro proceso podría crear mismo record
    - Resultado: IntegrityError por constraint UNIQUE
    - Current error handling: No visible (probablemente causa import failure parcial)

VECTOR 2: seed_zk_sql.py - MANAGEMENT COMMAND

  OPERATIVA ACTUAL:
    ```
    batch = []
    for row in file_rows:
        log = AttendanceLog(device_id=..., user_id=..., timestamp=..., ...)
        batch.append(log)
        if len(batch) >= batch_size:
            AttendanceLog.objects.bulk_create(batch, ignore_conflicts=True)
            batch = []
    
    if batch:
        AttendanceLog.objects.bulk_create(batch, ignore_conflicts=True)
    ```
  
  IDEMPOTENCIA APPROACH:
    ✓ ignore_conflicts=True → Si UNIQUE constraint viola, silenciosamente ignora
    ✓ Re-correr: Mismos rows → Mismos conflicts → Mismo resultado final
    ✓ Idempotent (by design) ✓
  
  Ventaja vs zk_workers.py: No requiere queries previas, batching es más eficiente

VECTOR 3: FileAttendanceAdapter - LEGACY

  Proceso (no usado actualmente):
    1. read_attendance() parses CSV/TXT/LOG
    2. Returns List[Dict] (NO persistence)
    3. Malformed lines: Silently skipped with `continue`
    4. No logging of skipped lines
  
  ⚠️ PROBLEMA CRÍTICO:
    - If same file reimported: Malformed lines again skipped (idempotent)
    - But NO AUDIT TRAIL de qué fue skipped
    - Imposible saber si un registro fue rechazado por malformed o si es record viejo
  
  Ejemplo problema:
    File v1: user_id,2026-02-03,0,0  ← Saved OK
    File v2: user_id,INVALID_DATE,0,0  ← Skipped, no log
    File v2 (retry): user_id,INVALID_DATE,0,0  ← Skipped again
    Result: Parece idempotent pero en realidad perdió un registro

VECTOR 4: Data in Device Memory (ZKTeco)

  ⚠️ FUENTE DE VERDAD MOLESTA:
    - Dispositivo ZKTeco almacena logs en memory (no persistente)
    - zk_workers.py:get_attendance() descarga y el dispositivo BORRA después
    - ¿Pero qué si descarga FALLA pero se borra medio?
    - ✓ Hay finally block para re-enable, pero NO guarantee de data consistency
  
  Observed in code:
    ```
    finally:
        try:
            zk_service.enable_device()
        except:
            pass
    zk_service.disconnect()
    ```
    ✓ Good: Re-enable en finally
    ⚠️ Bad: Silent exception catch
    ⚠️ Bad: No explicit rollback de descarga parcial

VECTOR 5: Bulk Operations via API

  AttendanceLogViewSet (viewsets.py #157-220):
    - No override de create()
    - perform_create() solo setea edited_by/edited_at si necesario
    - Luego serializer.save() → Django ORM .create()
  
  ⚠️ RIESGO:
    - Un client que POST mismo AttendanceLog 2x
    - Primera: 201 Created
    - Segunda: 400 Bad Request (UNIQUE constraint violation) ← No explicit handling
    - Resultado: NO IDEMPOTENT para APIs normales

VECTOR 6: Malformed Lines en File Import

  FileAttendanceAdapter malformed handling:
    ```
    try:
        user_id = row[0].strip()
        timestamp_str = row[1].strip()
        status = int(row[2].strip())  ← Puede fallar si no es int
        punch = int(row[3].strip())  ← Puede fallar si no es int
        timestamp = self._parse_timestamp(timestamp_str)  ← Puede fallar

    ```
  
  Problems:
    ❌ No logging de qué línea falló
    ❌ No count de skipped malformed
    ❌ No retorno de error details al caller

       Respuesta: Se re-skipa (idempotent pero opaco)

RESUMEN IDEMPOTENCIA:
  
  ✅ zk_workers.py: Idempotente pero sin atomicidad (risk de partial import)
  ✅ seed_zk_sql.py: Idempotente (ignore_conflicts=True)

  ❌ AttendanceLogViewSet: NO idempotente (constraint violation en POST 2x)
  
  RECOMENDACIÓN CRÍTICA:

    → Agregar ignore_conflicts option a AttendanceLogViewSet

PROBLEMA CRÍTICO: run_import_attendance_job() - NO TRANSACCIÓN

  ```python
  def run_import_attendance_job(job_id, device_id, overwrite=False, start_date=None):
      try:
          # ... connect, disable ...
          for att in records:
              if exists:
                  if overwrite:
                      AttendanceLog.objects.filter(...).update(...)
                  else:
                      skipped_count += 1
              else:
                  AttendanceLog.objects.create(...)  ← NO TRANSACTION
              imported_count += 1  ← Contador se incrementa AUNQUE create() pueda fallar
          # ... enable ...
      except Exception as e:
          JobManager.finish_job(job_id, "failed", str(e))
  ```
  
  ⚠️ FALLACY SCENARIOS:

  Scenario A: IntegrityError a la mitad de import
    1. Import comienza: records = [r1, r2, r3, r4, r5]
    2. r1, r2, r3 se crean OK → DB tiene 3 registros
    3. r4 falla con IntegrityError (duplicate by race condition)
    4. Exception caught, job marked "failed"
    5. BUT: r1, r2, r3 QUEDAN en la BD (PARTIAL IMPORT)
    6. Cliente ve: "failed" pero 3/5 registros fueron creados
    7. Retry: ¿User sabe que tiene que skip r1-r3? Imposible sin external_id
  
  Scenario B: Timeout intermedio
    1. Import comienza
    2. r1-r50 se crean
    3. Connection timeout en r51
    4. Exception caught, zk_service.disconnect()
    5. r1-r50 QUEDAN en BD
    6. Usuario manualmente retry
    7. r1-r50 detectados con .exists() y skipped
    8. r51-r100 se importan
    9. Result: OK pero con latency, usuario no sabe qué pasó

RECOMENDACIÓN:
  → Wrap run_import_attendance_job() entire import loop en transaction.atomic()
  → Si falla en cualquier punto: TOTAL ROLLBACK
  → Atomicity garantiza: Todo o Nada (no partial imports)

FASE 5: TIMEZONE Y CONSISTENCIA (✅ HALLAZGOS CRÍTICOS)
================================================================================

CONFIGURACIÓN DJANGO (settings.py):
  USE_TZ = True  ← Django usa UTC internally, convierte a TIME_ZONE para display
  TIME_ZONE = 'America/Argentina/Buenos_Aires'  ← Zona local (-03:00 UTC en verano)

TIMEZONE HANDLING POR VECTOR:

Vector 1: ZKTecoAdapter (PRODUCCIÓN)
  
  pyzk library retorna: datetime.datetime (NAIVE, sin tzinfo)
  Asunción de Django: NAIVE datetime está en TIME_ZONE configurado (Buenos Aires)
  
  Flujo actual:
    1. zk_service.get_attendance() → List[Attendance]
    2. att.timestamp → NAIVE datetime (ejemplo: 2026-02-03 17:07:07)
    3. Django asume: 2026-02-03 17:07:07 es en Buenos Aires (-03:00)
    4. Django convierte a UTC interno: 2026-02-03 20:07:07 UTC
    5. PostgreSQL guarda: 2026-02-03 20:07:07+00:00
  
  ✓ CORRECTO si: Dispositivo ZKTeco está configurado en zona Buenos Aires
  ❌ INCORRECTO si: Dispositivo está en zona diferente (e.g., UTC, America/Mexico_City)
  
  ⚠️ MISSING VALIDATION:
    - No campo timezone en Device model
    - No validación de timezone device vs sistema
    - No conversión explícita
  
  RECOMENDACIÓN:
    → Agregar field timezone a Device model
    → En zk_workers.py, hacer conversión explícita:
    ```python
    if device.timezone:
        dt_naive = att.timestamp
        dt_aware = timezone.make_aware(dt_naive, pytz.timezone(device.timezone))
    ```

Vector 2: FileAttendanceAdapter (LEGACY)
  
  Parsing: datetime.fromisoformat() o strptime()
  Result: NAIVE datetime + NO timezone conversion
  
  Luego cuando se persist:
    - Django asume timezone local (Buenos Aires)
    - Risk: Si archivo generado en otra zona → INCORRECTO
  
  STATUS: No usado en producción, pero riesgo si alguien lo usa

Vector 3: seed_zk_sql.py (Management command)
  
  ```python
  dt = parse_datetime(str(value))
  if timezone.is_naive(dt):
      dt = timezone.make_aware(dt, timezone.get_current_timezone())
  ```
  
  ✓ CORRECTO: Hace conversión explícita a timezone local
  ✓ ROBUSTO: Chequea si is_naive antes de convertir
  
Vector 4: attendance_engine.py (Cálculo)
  
  ```python
  search_start = timezone.make_aware(datetime.combine(target_date, time(0, 0)))
  search_end = timezone.make_aware(datetime.combine(target_date + timedelta(days=1), time(0, 0)))
  ```
  
  ✓ CORRECTO: Hace timezone.make_aware() para queries
  ✓ Busca logs entre 00:00 y 23:59:59 en timezone local
  
  PERO: Si AttendanceLog tiene timezone incorrecto, search resultará vacío

CRÍTICA DE TIMEZONE:

  🔴 ALTO RIESGO si dispositivo está en zona diferente a Buenos Aires
  
  Ejemplo problema:
    - Dispositivo en UTC (sin conversión)
    - Empleado marca entrada a las 2026-02-03 17:00:00 UTC
    - ZKTeco almacena: 2026-02-03 17:00:00
    - pyzk retorna: datetime(2026, 2, 3, 17, 0, 0)
    - Django asume Buenos Aires: 2026-02-03 17:00:00 -03:00
    - Actually fue: 2026-02-03 14:00:00 zona local
    - Error: +3 horas de desvío permanente en todos los logs
  
  IMPACTO EN CÁLCULO:
    - attendance_engine.py busca logs entre 00:00 y 23:59:59 local
    - Si logs tienen timezone incorrecto: Lo encuentra en fecha anterior/posterior
    - Resultado: Calculado en fecha incorrecta → Tarde/Ausencia falsa

RECOMENDACIÓN URGENTE:
  1. Agregar Device.timezone field (default: 'America/Argentina/Buenos_Aires')
  2. En zk_workers.py, hacer conversión:
     ```python
     device_tz = pytz.timezone(device.timezone)
     dt_aware = timezone.make_aware(att.timestamp, device_tz)
     att_log = AttendanceLog(timestamp=dt_aware, ...)
     ```
  3. En FileAttendanceAdapter (si se usa):
     ```python
     tz = pytz.timezone(source_device_timezone)
     timestamp = self._parse_timestamp(timestamp_str)
     timestamp_aware = timezone.make_aware(timestamp, tz)
     ```

FASE 6: ENGINES (V1 vs V2) Y SHADOW COMPARISON (✅ ANALIZADO)
================================================================================

ARQUITECTURA CÁLCULO:

  V1 (attendance_engine.py) - PRODUCCIÓN ACTUAL
    ├─ Entrada: AttendanceLog records para (employee, date)
    ├─ Procesamiento: Fixed schedule, Flex schedule, Overrides
    ├─ Salida: DailyAttendance (persistida)
    └─ Usado en: calculate_day() → API endpoint, batch operations
  
  V2 (attendance_engine_v2.py) - SHADOW MODE
    ├─ Entrada: Mismos AttendanceLog records
    ├─ Procesamiento: Algoritmo mejorado (unclear changes from docs)
    ├─ Salida: CalculationResult (NO persistida)
    └─ Usado en: ShadowComparisonService (para comparación)

SHADOW COMPARISON FLOW:

  1. Client calls: POST /api/v1/attendance/calculate/
  2. AttendanceApplicationService.process_daily_attendance()
  3. Executes V1 → Persists DailyAttendance
  4. STEP 6 (OUTSIDE transaction):
     ```python
     if self._shadow_enabled and daily is not None:
         self._run_shadow_comparison(employee, target_date, daily)
     ```
  5. ShadowComparisonService.run_shadow_for_day():
     ├─ Executes V2 (pure, no DB mutations)
     ├─ Compares: V1.worked_minutes vs V2.net_worked_minutes
     ├─ Creates ShadowCalculation record:
     │  ├─ v1_worked_minutes
     │  ├─ v2_worked_minutes, v2_net_minutes, v2_regular, v2_overtime, v2_night
     │  ├─ difference_minutes (V2 - V1)
     │  ├─ difference_type: MINOR (<30min), MEDIUM (30-120min), MAJOR (>120min), CRITICAL
     │  └─ requires_review (True if MAJOR or CRITICAL)
     └─ If shadow fails: Logged, but production V1 result NOT affected ✓

SHADOW CONFIG:
  AttendanceApplicationService.__init__:
    SHADOW_MODE_ENABLED = True  ← Hard-coded True
    enable_shadow: bool = True ← Default enabled
    self._shadow_enabled = enable_shadow and SHADOW_MODE_ENABLED
  
  Result: Shadow mode ALWAYS enabled unless explicitly disabled via parameter

SHADOW CONSISTENCY VALIDATION:

  ✓ Good Aspects:
    1. Runs AFTER V1 result is persisted (no risk to production)
    2. Error-isolated: If V2 fails, V1 result unaffected
    3. Fingerprint computed on punch_ids for traceability
    4. Difference classified as MINOR/MEDIUM/MAJOR/CRITICAL
    5. All inputs logged in ShadowCalculation record
    6. Can identify discrepancies trend before V2 migration
  
  ⚠️ Areas of Concern:
    1. No automatic alerting if CRITICAL differences detected
    2. ShadowCalculation created regardless of difference_type
       → Manual review required to identify systematic issues
    3. No rollback/correction mechanism between V1 and V2
       → Manual intervention needed if systematic errors found
    4. Difference classification thresholds fixed (30, 120 min)
       → Might not fit all departments/roles

SHADOW UTILITY FOR BETA:

  ✓ Excellent for pre-production validation
  ✓ Can identify V2 bugs before migration
  ✓ Builds confidence in V2 algorithm
  ✓ Provides data-driven migration plan
  
  Recommendation:
    → In Beta: Monitor ShadowCalculation daily
    → Set up alerts for CRITICAL differences
    → Collect metrics: % MINOR, MEDIUM, MAJOR, CRITICAL
    → Before RC2: Analysis of critical differences
    → Consider: Adjust thresholds based on data distribution

     → Riesgo: No logging de qué líneas fueron skipped
     → Imposible auditar qué registros fueron rechazados
     → Solución: Log skipped lines con índice y motivo
     → Impacto: No detecta corrupción de archivos importados
  
  5. [RACE CONDITION] ALTO | zk_workers.py | .exists() → .create() without lock
     → Risk: Entre check y create, otro proceso podría crear mismo registro
     → Likelihood: Bajo (background job típicamente serial), pero posible en concurrencia
     → Solución: O usar atomic(), O usar update_or_create(), O usar select_for_update()
     → Impacto: IntegrityError intermitente en cloud environments

  6. [VALIDATION] ALTO | AttendanceLog | user_id no es FK, puede ser orphan
     → Riesgo: user_id en ZKTeco que no existe en Employee table
     → Employee.objects.get(user_id=...) retorna None en serializer
     → Resultado: Registros que no pueden asignarse a empleado
     → Solución: O validar FK en serializer, O crear placeholder Employee
     → Impacto: Data loss conceptual - logs sin empleado no procesables
