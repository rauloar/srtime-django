1.2 FLUJO DE RESOLUCIÓN DE HORARIOS
---

FUNCIÓN PRINCIPAL: resolve_schedule_unified(employee_id, target_date)
  Ubicación: core/services/schedule_resolver.py:72

PRIORIDAD (Order of Operations):

  PASO 1: ScheduleOverride
    ├─ Query: ScheduleOverride.objects.filter(employee_id, date=target_date)
    ├─ Si existe: Devuelve timetable asociado
    ├─ Fuente: ScheduleSource.OVERRIDE
    └─ Nota: Sobrescritura puntual (máxima prioridad)
    
  PASO 2: EmployeeShift (scope='EMPLOYEE')
    ├─ Query: EmployeeShift.objects.filter(
    │           scope='EMPLOYEE',
    │           employee_id,
    │           start_date__lte=target_date,
    │           end_date__gte=target_date OR end_date__isnull=True
    │         )
    ├─ Si existe: Resuelve timetable del shift para el día
    ├─ Fuente: ScheduleSource.EMPLOYEE_SHIFT
    └─ Nota: Asignación individual tiene prioridad sobre empresa
    
  PASO 3: EmployeeShift (scope='DEPARTMENT')
    ├─ Obtiene department del employee
    ├─ Query: EmployeeShift.objects.filter(
    │           scope='DEPARTMENT',
    │           department_id=emp.department.id,
    │           start_date__lte=target_date,
    │           end_date__gte=target_date OR end_date__isnull=True
    │         )
    ├─ Si existe: Resuelve timetable del shift para el día
    ├─ Fuente: ScheduleSource.DEPARTMENT_SHIFT
    └─ Nota: Fallback si no hay asignación individual
    
  PASO 4: Implicit Rest Day
    ├─ Si nada anterior devuelve match
    ├─ Fuente: ScheduleSource.IMPLICIT_REST
    ├─ Estado: is_valid=False, error=NO_SHIFT_ASSIGNED
    └─ Interpretación: Día libre (sin horario asignado)

1.3 RESOLUCIÓN DE TIMETABLE(s) DENTRO DE UN SHIFT
---

FUNCIÓN: _resolve_shift_timetable(shift, emp_shift, target_date)
  Ubicación: core/services/schedule_resolver.py:226

LÓGICA:

  1. Check shift.ShiftTimetables existen
     └─ Si no: Error SHIFT_NO_TIMETABLES
     
  2. Calcular day_index
     ├─ Si shift.cycle_days > 0 (ciclo largo):
     │   └─ day_index = (target_date - emp_shift.start_date).days % shift.cycle_days
     │
     └─ Si shift.cycle_days == 0 (ciclo semanal):
         └─ day_index = target_date.weekday()  # 0=Lun, 6=Dom
         
  3. Buscar ShiftTimetable
     ├─ Query: ShiftTimetable.objects.filter(
     │           shift=shift,
     │           day_index=day_index
     │         ).select_related('timetable')
     ├─ Si existe: Devuelve (shift_tt, None)
     └─ Si no: Devuelve (None, SHIFT_TIMETABLE_MISSING_DAY)
     
  4. Devolver Timetable
     └─ Se envuelve en ResolvedSchedule con on_duty_dt y off_duty_dt

1.4 REGLAS DE OVERNIGHT SHIFTS
---

ESPECIAL: Turnos Nocturnos (off_duty < on_duty)

En _build_resolved_schedule():
  
  if on_duty_time and off_duty_time:
    if off_duty_time < on_duty_time:
      # Es un turno nocturno (cruza medianoche)
      off_duty_dt = datetime.combine(target_date + timedelta(days=1), off_duty_time)
    else:
      off_duty_dt = datetime.combine(target_date, off_duty_time)

Ejemplo:
  ├─ on_duty = 22:00
  ├─ off_duty = 06:00
  ├─ target_date = 2026-02-10
  └─ Resultado:
      ├─ on_duty_dt = 2026-02-10 22:00
      └─ off_duty_dt = 2026-02-11 06:00

2.1 ESCENARIOS EDGE ANALIZADOS

ESCENARIO A: Múltiples EmployeeShift (scope='EMPLOYEE') activos en la misma fecha
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ejemplo:
  ├─ EmployeeShift #1: Shift "Mañana" (2026-02-01 → 2026-02-14)
  ├─ EmployeeShift #2: Shift "Tarde" (2026-02-10 → 2026-02-20)
  └─ target_date = 2026-02-10

Comportamiento ACTUAL:
  ├─ Query: .filter(...start_date__lte=target_date).filter(Q(end_date__gte=target_date) | Q(end_date__isnull=True)).first()
  ├─ `.first()` → Devuelve PRIMERA coincidencia en orden DB (orden por ordering=['-start_date'])
  └─ RESULTADO: Devuelve Shift "Tarde" (porque tiene start_date más reciente)

¿Es determinístico?
  ├─ SÍ: La QuerySet tiene ordering=['-start_date']
  ├─ PERO: Si dos ShiftAssignments tienen MISMO start_date, el resultado es impredecible
  └─ RIESGO: BAJO → Prácticamente imposible que dos tengan el mismo start_date

RECOMENDACIÓN:
  └─ Hacer explícita la prioridad con una columna `priority` O validar en DB que no haya overlaps


ESCENARIO B: Departamento tiene múltiples EmployeeShift (scope='DEPARTMENT') activos
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ejemplo:
  ├─ DeptShift #1: Turno "A" (2026-02-01 → 2026-02-14)
  ├─ DeptShift #2: Turno "B" (2026-02-10 → 2026-02-20)
  ├─ Employee Mary es del Department
  └─ target_date = 2026-02-10

Comportamiento ACTUAL:
  ├─ No hay asignación individual (scope='EMPLOYEE')
  ├─ Fallback a scope='DEPARTMENT'
  ├─ `.first()` → Devuelve PRIMERA (Turno "B", porque start_date más reciente)
  └─ RESULTADO: Mary realiza cálculo con Turno "B"

¿Es determinístico?
  ├─ SÍ: Mismo ordering=['-start_date']
  ├─ PERO: Si dos DeptShifts tienen MISMO start_date → impredecible
  └─ RIESGO: BAJO → Rarísimo en operación normal (requiere error de datos)

RECOMENDACIÓN:
  └─ Validar en DB (constraint único de (scope, employee_id/department_id, start_date, end_date))


ESCENARIO C: Turno sin ShiftTimetables configurados
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  └─ target_date solicitado

Comportamiento ACTUAL:

  └─ RESULTADO: Treated as IMPLICIT_REST (is_absent=True)

¿Es determinístico?
  ├─ SÍ: La lógica es explícita
  └─ RIESGO: MEDIO → El empleado se cuenta como ausente silenciosamente si admin olvida configurar

ESCENARIO D: Shift sin ningún ShiftTimetable para el día (ej: no hay viernes en ciclo)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ejemplo:
  ├─ Shift "4x3" (4 días ON, 3 días OFF)
  ├─ Configurado: ShiftTimetables para días 0,1,2,3
  ├─ Employee: Turno inicio 2026-02-01
  └─ target_date = 2026-02-13 (sábado, day_index=5 en ciclo, pero no configurado)

Cálculo:
  ├─ cycle_days = 7
  ├─ day_index = (2026-02-13 - 2026-02-01).days % 7 = 12 % 7 = 5
  ├─ ShiftTimetable.filter(shift=shift, day_index=5) → NO EXISTE
  ├─ Retorna: (None, SHIFT_TIMETABLE_MISSING_DAY)
  └─ RESULTADO: ResolvedSchedule(is_valid=False, implicit REST)

¿Es determinístico?
  ├─ SÍ: Cálculo matemático claro
  └─ RIESGO: BAJO → Es comportamiento intencional
     (El admin sabe qué días no trabaja)

2.3 POSIBLES DECISIONES IMPLÍCITAS
---

1. MÚLTIPLES ASIGNACIONES ACTIVAS (scope='EMPLOYEE')
   ├─ Decisión: Usar la con start_date MAYOR (más reciente)
   ├─ Implícita: SI (no documentada, implícita en .order_by('-start_date').first())
   ├─ Riesgo: Si dos tienen exactamente same start_date → DB order (id)
   └─ Recomendación: Hacer explícita con constraint UNIQUE en DB

2. FALLBACK EMPLOYEE → DEPARTMENT
   ├─ Decisión: Si no hay scope='EMPLOYEE', usar scope='DEPARTMENT'
   ├─ Implícita: SÍ (pero lógica es clara en código)
   ├─ Riesgo: Bajo (es esperado)
   └─ Recomendación: Ya está bien documentado

3. HORARIO NOCTURNÓ (off_duty < on_duty)
   ├─ Decisión: Asignar off_duty al día siguiente
   ├─ Implícita: SÍ (no hay UI hint)
   ├─ Riesgo: Bajo (es estándar en HR)
   └─ Recomendación: Documentar en Timetable model

4. CICLO LARGO CON start_date
   ├─ Decisión: day_index = (target_date - start_date).days % cycle_days
   ├─ Implícita: SÍ (start_date DEBE existir, no está validado)
   ├─ Riesgo: MEDIO (puede fallar silenciosamente si start_date=NULL)
   └─ Recomendación: VALIDAR EN MODELO

5. IMPLICIT REST (Sin asignación)
   ├─ Decisión: No schedule = trabajó 0 min, ausente
   ├─ Implícita: SÍ (podría ser "flexible day")
   ├─ Riesgo: Bajo (comportamiento esperado)
   └─ Recomendación: Ya documentado

CAMBIO #1: Validar start_date para ciclos largos
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Agregación:
  ```python
  def clean(self):  # Validation en modelo
      from django.core.exceptions import ValidationError
      
      # Si el shift tiene cycle_days > 0, start_date MUST exist
      if self.shift and self.shift.cycle_days and self.shift.cycle_days > 0:
          if not self.start_date:
              raise ValidationError({
                  'start_date': 'start_date es requerido cuando el turno tiene ciclo largo'
              })
      
      # Opcional: Validar que start_date <= end_date (si end_date existe)
      if self.start_date and self.end_date:
          if self.start_date > self.end_date:
              raise ValidationError({
                  'end_date': 'end_date debe ser >= start_date'
              })
  ```
